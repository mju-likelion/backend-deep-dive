# LLM Evaluation & Operations

LLM 기반 애플리케이션의 품질을 지속적으로 평가하고 안정적으로 운영하기 위한 방법을 정리한다.

이 문서에서는 다음 내용을 다룬다.

- 골든셋 구성과 회귀 테스트
- 회귀 테스트를 CI에 적용하는 방법
- LLM-as-a-Judge의 편향과 보정
- 프롬프트 버저닝과 배포 전략
- 트레이싱
- 사용자 피드백을 평가셋으로 회수하는 루프
- 프롬프트 변경 PR이 골든셋 점수를 떨어뜨리면 CI가 실패하는 데모

---

# 1. Golden Set

## 1.1 골든셋이란

골든셋(Golden Set)은 **정답 또는 기대 결과가 검증된 평가용 데이터 집합**이다.

LLM의 성능을 평가하려면 모델이 생성한 답변이 올바른지 판단할 기준이 필요하다.

예를 들어 다음과 같이 구성할 수 있다.

```text
문제: 대한민국의 수도는 어디인가?
정답: 서울
```

```text
문제: 2 + 3 × 4의 값은 얼마인가?
정답: 14
```

단순히 질문만 모아놓는 것이 아니라 사람이 검토하거나 신뢰할 수 있는 자료를 통해 **기대 결과가 검증되어 있어야 한다.**

기본적인 평가 흐름은 다음과 같다.

```text
Golden Set
    ↓
LLM에게 문제 입력
    ↓
모델 답변 생성
    ↓
Golden Answer와 비교
    ↓
점수 계산
```

예를 들어 골든셋이 100문항이고 모델이 90문항을 올바르게 처리했다면 정확도를 90%로 계산할 수 있다.

---

## 1.2 골든셋 유지보수

골든셋은 한 번 만들고 끝나는 데이터가 아니다.

서비스 정책, 데이터, 사용자 질문 방식, 모델의 실패 유형은 계속 변경될 수 있기 때문이다.

대표적인 유지보수 작업은 다음과 같다.

- 잘못된 정답을 수정한다.
- 애매한 문제를 제거하거나 수정한다.
- 중복 문제를 제거한다.
- 새롭게 발견된 실패 사례를 추가한다.
- 서비스 정책 변경에 따라 정답을 수정한다.
- 특정 유형의 데이터가 부족하면 보충한다.

예를 들어 기존에는 회원 탈퇴 이후 포인트가 유지되었지만 정책이 변경되어 포인트가 소멸하도록 바뀌었다면 골든셋의 정답도 변경해야 한다.

다만 골든셋을 지속적으로 수정하면 과거 모델과 현재 모델의 성능을 동일한 기준으로 비교하기 어려워질 수 있다.

따라서 골든셋도 버전을 관리하는 것이 좋다.

```text
Golden Set v1.0
      ↓
Golden Set v1.1
      ↓
Golden Set v2.0
```

평가 결과에는 어떤 골든셋 버전을 사용했는지 함께 기록한다.

```text
Model: A
Golden Set: v1.2
Accuracy: 91.5%
```

# 2. Bucket과 Slice

전체 정확도 하나만 보면 모델이 어느 영역에서 강하고 약한지 알기 어렵다.

이를 세부적으로 분석하기 위해 버킷과 슬라이스를 사용한다.

---

## 2.1 Bucket

버킷(Bucket)은 평가 문제를 **큰 능력이나 분야별로 나눈 집합**이다.

예를 들어 다음과 같이 구성할 수 있다.

| Bucket | 평가 내용 |
|---|---|
| 지식 QA | 일반 지식과 사실 질문 |
| 코드 생성 | 프로그래밍 문제 |
| 수학·논리 | 계산 및 추론 |
| 한국어 이해 | 문맥 이해 및 생성 |

전체 정확도가 90%라고 하더라도 버킷별 결과는 다음과 같이 다를 수 있다.

```text
전체 정확도: 90%

지식 QA: 72%
코드 생성: 98%
수학·논리: 96%
한국어 이해: 94%
```

이를 통해 전체 점수만 볼 때는 알 수 없었던 모델의 약점을 발견할 수 있다.

즉 버킷은 다음 질문에 답하기 위해 사용한다.

> 모델이 어떤 능력을 잘하고 못하는가?

---

## 2.2 Slice

슬라이스(Slice)는 평가 데이터에 **특정 조건을 걸어 일부 데이터만 필터링하여 분석하는 방식**이다.

예를 들어 다음과 같은 조건을 설정할 수 있다.

```text
난이도 = 어려움
```

```text
부정문 포함 = true
```

```text
문제 길이 > 500자
```

```text
프로그래밍 언어 = Java
```

전체 평가셋이 100문제이고 어려운 문제 25개만 선택했을 경우 다음과 같이 평가할 수 있다.

```text
전체 정확도: 90%

난이도 = 어려움
→ 25문제
→ 정확도 67%
```

따라서 버킷과 슬라이스는 다음과 같이 구분할 수 있다.

> Bucket은 **어떤 능력을 평가하는가**를 본다.  
> Slice는 **어떤 조건에서 성능이 달라지는가**를 본다.

---

# 3. Regression Test

회귀 테스트(Regression Test)는 **새로운 변경 이후 기존에 정상적으로 동작하던 성능이 떨어지지 않았는지 확인하는 테스트**다.

LLM 애플리케이션에서는 다음과 같은 변경 이후 회귀가 발생할 수 있다.

- 프롬프트 변경
- 모델 변경
- RAG 검색 방식 변경
- Tool 호출 방식 변경
- 시스템 프롬프트 변경
- 출력 형식 변경

예를 들어 기존 프롬프트의 성능이 다음과 같다고 가정한다.

```text
Prompt v1

수학: 80점
코드: 90점
한국어: 95점
```

프롬프트 변경 이후 다음과 같이 나올 수 있다.

```text
Prompt v2

수학: 95점
코드: 95점
한국어: 85점
```

전체적인 성능은 좋아졌지만 기존에 잘하던 한국어 영역에서 10점이 떨어졌다.

이러한 성능 저하를 회귀라고 한다.

회귀 테스트의 기본 흐름은 다음과 같다.

```text
기존 Prompt / Model
        ↓
Golden Set 평가
        ↓
Prompt / Model 변경
        ↓
동일한 Golden Set 평가
        ↓
이전 결과와 비교
        ↓
성능 하락 여부 확인
```

# 4. Golden Set 기반 회귀 테스트를 CI에 넣기

CI는 Continuous Integration의 약자로 지속적 통합을 의미한다.

코드가 Push되거나 Pull Request가 생성될 때 자동으로 빌드와 테스트를 실행한다.

일반적인 CI 흐름은 다음과 같다.

```text
Push / Pull Request
        ↓
CI 실행
        ↓
Build
        ↓
Unit Test
        ↓
Integration Test
        ↓
결과 확인
```

LLM 애플리케이션에서는 여기에 골든셋 기반 평가를 추가할 수 있다.

```text
Pull Request
      ↓
CI 실행
      ↓
기존 Prompt 평가
      ↓
변경 Prompt 평가
      ↓
Golden Set 점수 비교
      ↓
Regression 확인
      ↓
PASS / FAIL
```

예를 들어 다음과 같은 기준을 설정할 수 있다.

```text
전체 정확도 >= 90%

기존 버전 대비
전체 점수 하락 <= 5%p

중요 Bucket 점수 >= 85%
```

기존 버전이 93%, 새 버전이 92%라면 허용 범위 내이므로 통과시킬 수 있다.

반면 다음과 같다면 실패시킬 수 있다.

```text
Baseline: 93%
Candidate: 84%

Score Drop: 9%p

→ Regression detected
→ CI FAIL
```

이렇게 하면 사람이 매번 직접 평가하지 않아도 프롬프트 변경으로 인한 품질 저하를 자동으로 탐지할 수 있다.

# 5. LLM-as-a-Judge

LLM-as-a-Judge는 **LLM을 사용하여 다른 LLM의 답변 품질을 평가하는 방식**이다.

예를 들어 다음과 같이 사용할 수 있다.

```text
질문
 │
 ├─ Model A 답변
 │
 └─ Model B 답변
        ↓
     Judge LLM
        ↓
    답변 품질 평가
```

객관식이나 단순 계산 문제는 정답 비교로 쉽게 평가할 수 있다.

하지만 다음과 같은 문제는 단순 문자열 비교로 평가하기 어렵다.

- 설명이 이해하기 쉬운가
- 사용자의 지시사항을 잘 따랐는가
- 문장이 자연스러운가
- 답변이 충분한가
- 불필요한 내용을 생성하지 않았는가

이러한 경우 LLM-as-a-Judge를 활용할 수 있다.

하지만 Judge 역시 LLM이므로 여러 편향이 발생할 수 있다.

---

# 6. LLM-as-a-Judge의 편향

## 6.1 Position Bias

위치 편향(Position Bias)은 답변의 품질과 관계없이 **앞이나 뒤에 배치된 답변을 더 선호하는 현상**이다.

예를 들어 다음과 같이 평가한다.

```text
A: Model 1 답변
B: Model 2 답변
```

Judge가 A를 선택했다고 해서 반드시 Model 1의 답변이 더 우수하다고 할 수 없다.

Judge가 첫 번째 위치를 선호했을 가능성도 있기 때문이다.

이를 완화하기 위해 답변 순서를 바꾸어 다시 평가할 수 있다.

```text
1차 평가
A: Model 1
B: Model 2

2차 평가
A: Model 2
B: Model 1
```

즉 AB / BA 방식으로 평가한다.

---

## 6.2 Verbosity Bias

길이 편향(Verbosity Bias)은 Judge가 **더 길고 자세한 답변을 더 좋은 답변이라고 판단하는 현상**이다.

예를 들어 다음 두 답변은 모두 정답일 수 있다.

```text
A:
서울이다.
```

```text
B:
대한민국의 수도는 서울특별시이다.
서울은 대한민국의 정치, 경제, 문화 중심지이며...
```

평가 목표가 단순히 정확성이라면 두 답변 모두 정답으로 처리되어야 한다.

하지만 Judge가 길이가 긴 B를 더 높은 품질이라고 판단할 수 있다.

이를 줄이기 위해 Judge 프롬프트에 다음과 같이 명시한다.

```text
답변 길이 자체는 평가 기준에 포함하지 않는다.
정확성과 요구사항 충족 여부를 중심으로 평가한다.
```

---

## 6.3 Style Bias

Judge가 Markdown, 표, 제목, 단계별 설명 등 특정 표현 방식을 더 선호할 수 있다.

예를 들어 내용이 동일하더라도 다음과 같이 보기 좋게 작성된 답변을 더 좋은 답변이라고 판단할 수 있다.

```text
## 정답

14

### 풀이

1. 곱셈을 먼저 수행한다.
2. 3 × 4 = 12
3. 2 + 12 = 14
```

평가 목적이 정확성이라면 이러한 스타일 요소가 점수를 과도하게 좌우해서는 안 된다.

따라서 명확한 Rubric을 제공해야 한다.

---

## 6.4 Self-preference Bias

Judge가 자기 자신 또는 자신과 비슷한 모델의 답변 스타일을 더 선호할 가능성이 있다.

이를 줄이기 위해 서로 다른 계열의 Judge를 사용할 수 있다.

```text
Judge 1
Judge 2
Judge 3
```

여러 Judge의 결과를 비교하거나 다수결을 적용하면 특정 Judge 하나의 편향을 줄일 수 있다.

---

## 6.5 Judge 자체의 오류

Judge도 LLM이므로 잘못된 평가를 할 수 있다.

Candidate 답변이 틀렸지만 매우 그럴듯하게 작성되어 있다면 Judge가 높은 점수를 줄 가능성도 있다.

따라서 가능하면 다음 정보를 함께 제공하는 것이 좋다.

```text
질문
+
Golden Answer
+
Candidate Answer
+
Evaluation Rubric
```

---

# 7. Rubric

Rubric은 **무엇을 어떤 기준으로 평가할지 정의한 채점 기준표**다.

단순히 다음과 같이 요청하는 것은 모호하다.

```text
이 답변이 좋은지 평가해라.
```

대신 다음과 같이 명확하게 평가 기준을 정의할 수 있다.

```text
정확성: 50점
지시사항 준수: 30점
명확성: 20점

답변 길이와 Markdown 사용 여부는 평가하지 않는다.
```

Rubric이 명확할수록 Judge가 임의의 기준으로 평가하는 것을 줄일 수 있다.

---

# 8. LLM-as-a-Judge 편향 보정

대표적인 편향과 보정 방법은 다음과 같다.

| 문제 | 보정 방법 |
|---|---|
| Position Bias | 답변 순서를 바꾸거나 무작위화한다. |
| Verbosity Bias | 답변 길이를 평가하지 않도록 명시한다. |
| Style Bias | 명확한 Rubric을 제공한다. |
| Self-preference Bias | 서로 다른 계열의 Judge를 사용한다. |
| Judge 오류 | Golden Answer 또는 근거를 제공한다. |
| Judge 간 불일치 | 여러 Judge의 결과를 비교한다. |
| 애매한 평가 | Human Review를 수행한다. |

전체 흐름은 다음과 같이 구성할 수 있다.

```text
Golden Set
    ↓
Model A / Model B
    ↓
Judge 1 / Judge 2
    ↓
결과 비교
    ↓
순서 변경 후 재평가
    ↓
그래도 불일치
    ↓
Human Review
```

핵심은 **하나의 Judge 결과를 절대적인 정답으로 취급하지 않는 것**이다.

# 9. Prompt Versioning

프롬프트 버저닝(Prompt Versioning)은 **프롬프트도 코드처럼 버전을 부여하고 변경 이력을 관리하는 것**이다.

프롬프트는 작은 문장 하나만 수정해도 LLM의 출력 결과에 영향을 줄 수 있다.

예를 들어 다음과 같이 관리할 수 있다.

```text
Prompt v1.0

사용자의 질문에 친절하게 답변한다.
```

이후 답변이 지나치게 길다는 문제가 발생하면 수정한다.

```text
Prompt v1.1

사용자의 질문에 핵심만 간결하게 답변한다.
```

환각을 줄이기 위해 다시 수정할 수도 있다.

```text
Prompt v1.2

사용자의 질문에 핵심만 간결하게 답변한다.
확실하지 않은 정보는 추측하지 않는다.
```

프롬프트 버전을 관리하면 어떤 변경으로 인해 성능이 좋아졌거나 나빠졌는지 확인할 수 있다.

다음과 같은 정보를 함께 관리할 수 있다.

| 항목 | 예시 |
|---|---|
| Prompt Version | v1.2 |
| 변경 내용 | 추측 금지 지시 추가 |
| Model | Model A |
| Golden Set | v2.1 |
| 평가 점수 | 94% |
| 상태 | Production |

문제가 발생하면 이전 버전으로 롤백할 수도 있다.

```text
Prompt v1.4
      ↓
문제 발생
      ↓
Rollback
      ↓
Prompt v1.3
```

# 10. Prompt Deployment Strategy

새 프롬프트를 만들었다고 바로 모든 사용자에게 적용하는 것은 위험할 수 있다.

평가셋에서는 좋은 성능을 보였지만 실제 사용자 환경에서는 예상하지 못한 문제가 발생할 수 있기 때문이다.

대표적인 배포 전략은 다음과 같다.

---

## 10.1 Full Deployment

새 프롬프트를 모든 사용자에게 바로 적용한다.

```text
Prompt v1
    ↓
Prompt v2
    ↓
100% 사용자 적용
```

구현은 가장 간단하지만 문제가 발생하면 모든 사용자에게 즉시 영향을 준다.

---

## 10.2 Canary Deployment

Canary 배포는 새 프롬프트를 **일부 사용자에게 먼저 적용한 후 점진적으로 확대하는 방식**이다.

```text
90% → Prompt v1
10% → Prompt v2
```

문제가 없다면 비율을 확대한다.

```text
10%
 ↓
30%
 ↓
50%
 ↓
100%
```

Canary의 주요 목적은 다음과 같다.

> 새 버전이 실제 운영 환경에서 안전한가?

---

## 10.3 A/B Test

A/B 테스트는 두 프롬프트를 동시에 운영하면서 **어느 버전이 더 좋은지 비교하는 방식**이다.

```text
A Group → Prompt v1
B Group → Prompt v2
```

다음과 같은 지표를 비교할 수 있다.

| 지표 | v1 | v2 |
|---|---:|---:|
| 정확도 | 89% | 94% |
| 사용자 만족도 | 4.1 | 4.4 |
| 평균 응답 시간 | 2.1초 | 2.4초 |
| 평균 비용 | $0.003 | $0.005 |

Canary와 A/B Test의 차이는 다음과 같다.

> Canary는 **안전한가**를 확인한다.  
> A/B Test는 **어느 것이 더 좋은가**를 비교한다.

---

## 10.4 Shadow Deployment

Shadow 배포는 기존 버전의 답변만 사용자에게 보여주고 새로운 버전은 뒤에서 동시에 실행하는 방식이다.

```text
사용자 질문
     │
     ├─ Prompt v1
     │      ↓
     │  사용자에게 응답
     │
     └─ Prompt v2
            ↓
        내부 평가만 수행
```

사용자에게 위험을 주지 않고 실제 사용자 입력을 기반으로 새로운 프롬프트를 테스트할 수 있다.

다만 두 버전을 동시에 실행하기 때문에 비용이 증가할 수 있다.

---

## 10.5 배포 전략 요약

| 전략 | 목적 |
|---|---|
| Full Deployment | 빠른 전체 적용 |
| Canary | 안전성 검증 |
| A/B Test | 성능 비교 |
| Shadow | 사용자에게 노출하지 않고 실제 트래픽 검증 |

# 11. Tracing

트레이싱(Tracing)은 **AI 요청 하나가 들어온 순간부터 최종 응답이 반환될 때까지 전체 과정을 추적하는 것**이다.

예를 들어 사용자가 다음과 같이 질문한다고 가정한다.

```text
회원 탈퇴하면 포인트가 어떻게 되나요?
```

내부에서는 다음과 같은 과정이 발생할 수 있다.

```text
사용자 입력
    ↓
프롬프트 생성
    ↓
검색 / DB 조회
    ↓
LLM 호출
    ↓
답변 생성
    ↓
후처리
    ↓
최종 응답
```

하나의 Trace에는 다음과 같은 데이터를 기록할 수 있다.

| 항목 | 예시 |
|---|---|
| Input | 회원 탈퇴하면 포인트가 어떻게 되나요? |
| Output | 회원 탈퇴 시 포인트는 소멸한다. |
| Prompt Version | v1.4 |
| Model | Model A |
| Input Token | 1,200 |
| Output Token | 350 |
| Total Token | 1,550 |
| Cost | $0.01 |
| Latency | 2.3초 |

---

## 11.1 Input / Output

Input에는 다음이 포함될 수 있다.

- 사용자 질문
- 시스템 프롬프트
- RAG 검색 결과
- Tool 결과
- 대화 문맥

Output은 LLM이 생성한 최종 답변이다.

잘못된 답변이 발생했을 때 당시 어떤 입력이 들어갔는지 확인할 수 있다.

---

## 11.2 Token

LLM은 텍스트를 Token 단위로 처리한다.

```text
Input Token
+
Output Token
=
Total Token
```

프롬프트를 변경한 이후 토큰 사용량이 크게 증가할 수도 있다.

```text
Prompt v1.3
평균 1,200 tokens

Prompt v1.4
평균 4,800 tokens
```

이를 통해 프롬프트가 불필요하게 길어졌거나 모델이 지나치게 긴 답변을 생성하고 있는지 확인할 수 있다.

---

## 11.3 Cost

API 기반 LLM은 모델과 토큰 사용량에 따라 비용이 발생한다.

기능별 비용을 추적하면 어떤 기능이 가장 많은 비용을 사용하는지 확인할 수 있다.

```text
전체 평균 비용: $0.004

RAG: $0.006
일반 QA: $0.002
```

---

## 11.4 Latency

Latency는 사용자 요청 이후 최종 응답이 반환될 때까지 걸리는 시간이다.

전체 시간뿐 아니라 단계별 시간을 기록하면 병목을 찾기 쉽다.

```text
총 응답 시간: 8.2초

검색:      0.8초
DB 조회:   0.3초
LLM 호출:  6.7초
후처리:    0.4초
```

이 경우 가장 큰 병목은 LLM 호출이라는 사실을 확인할 수 있다.

# 12. Logging과 Tracing의 차이

Logging은 개별 이벤트를 기록하는 것에 가깝다.

예를 들어 다음과 같다.

```text
14:01 사용자 요청 수신
14:01 DB 조회 완료
14:02 LLM 호출 완료
```

Tracing은 이러한 이벤트들을 **하나의 요청 흐름으로 연결하여 본다.**

```text
Trace #1234

Input
 ↓
DB
 ↓
Retriever
 ↓
LLM
 ↓
Output
```

즉 다음과 같이 이해할 수 있다.

> Logging은 개별 기록을 본다.  
> Tracing은 요청 하나의 전체 흐름을 본다.

# 13. User Feedback Loop

평가셋은 개발자가 처음 만든 데이터만으로 유지해서는 실제 사용 환경을 충분히 반영하기 어렵다.

실제 사용자는 개발자가 예상하지 못한 표현과 방식으로 질문하기 때문이다.

예를 들어 개발자는 다음과 같은 질문을 예상할 수 있다.

```text
환불 가능 기간은 며칠인가?
```

하지만 실제 사용자는 다음과 같이 질문할 수 있다.

```text
어제 결제했는데 지금 취소하면 돈 다 돌려받을 수 있나요?
```

같은 의도이지만 표현 방식은 크게 다르다.

따라서 실제 사용자 환경에서 발견된 실패 사례를 다시 평가셋에 반영해야 한다.

---

## 13.1 사용자 피드백 수집

다음과 같은 데이터를 수집할 수 있다.

- 👍 / 👎
- 별점
- 자유 의견
- 답변 재생성
- 재질문
- 신고
- 상담원 연결
- 사용자의 수정 요청

예를 들어 다음과 같은 상황이 발생할 수 있다.

```text
사용자:
회원 탈퇴하면 포인트가 어떻게 되나요?

AI:
포인트는 그대로 유지됩니다.

사용자:
👎
```

실제 정책이 포인트 소멸이라면 중요한 실패 사례가 된다.

---

## 13.2 사용자 피드백을 바로 골든셋에 넣으면 안 되는 이유

사용자가 👎을 눌렀다고 해서 해당 데이터를 바로 골든셋에 추가하면 안 된다.

사용자가 답변 스타일을 마음에 들어 하지 않았을 수도 있고 사용자가 잘못된 정보를 알고 있을 수도 있기 때문이다.

따라서 검증 과정이 필요하다.

```text
User Feedback
      ↓
실패 사례 후보 수집
      ↓
실제로 잘못된 답변인지 확인
      ↓
중복 여부 확인
      ↓
정답을 명확히 정의할 수 있는가
      ↓
Human Review
      ↓
Golden Answer 확정
      ↓
Golden Set 추가
```

즉 다음과 같이 이해할 수 있다.

> 사용자 피드백은 평가셋 후보 데이터다.  
> 검증된 사용자 피드백이 골든셋이 된다.

---

# 14. 전체 Feedback Loop

실제 운영에서는 다음 구조가 계속 반복된다.

```text
Golden Set
    ↓
Prompt 평가
    ↓
Regression Test
    ↓
배포
    ↓
실제 사용자 사용
    ↓
Tracing
    ↓
User Feedback
    ↓
Failure Case
    ↓
Human Review
    ↓
Golden Set 업데이트
    ↓
Prompt 개선
    ↓
다시 평가
```

평가셋이 실제 사용자의 실패 사례를 지속적으로 반영하면서 서비스 품질도 개선된다.

# 15. Demo

## 프롬프트 변경 PR이 골든셋 점수를 떨어뜨리면 CI가 실패하는 파이프라인

이번 데모의 목적은 다음과 같다.

> 프롬프트 변경으로 기존 성능이 떨어졌을 때 이를 자동으로 탐지하고 CI를 실패시키는 구조를 구현한다.

전체 구조는 다음과 같다.

```text
Prompt 변경
    ↓
Pull Request
    ↓
CI 실행
    ↓
Baseline Prompt 평가
    ↓
Candidate Prompt 평가
    ↓
Golden Set 점수 비교
    ↓
허용 범위 이상 하락?
    ↓
YES → CI FAIL
NO  → CI PASS
```

## 15.2 Golden Set

데모에서는 5개의 문제를 사용한다.

```text
Q1 대한민국의 수도는 어디인가?

Q2 2 + 3 * 4는 얼마인가?

Q3 HTTP 상태 코드 404는 무엇을 의미하는가?

Q4 Java에서 클래스를 상속할 때 사용하는 키워드는?

Q5 SQL에서 데이터를 조회할 때 사용하는 명령어는?
```

정답은 다음과 같다.

```text
Q1 → 서울
Q2 → 14
Q3 → 찾을 수 없음
Q4 → extends
Q5 → SELECT
```

## 15.3 평가 결과

실제 LLM을 호출하여 골든셋을 평가한 결과 다음과 같이 나타났다.

```text
Q1 PASS
Q2 PASS
Q3 PASS
Q4 PASS
Q5 PASS

Score: 5/5
Accuracy: 100%
```

즉 현재 기준 평가에서는 모든 골든셋 문제를 통과했다.

## 15.4 evaluate.py 역할

`evaluate.py`는 다음과 같은 역할을 한다.

```text
system.txt 읽기
       ↓
golden_set.json 읽기
       ↓
LLM API 호출
       ↓
모델 답변 생성
       ↓
Golden Answer 포함 여부 확인
       ↓
PASS / FAIL
       ↓
Accuracy 계산
       ↓
score.txt 저장
```

---

## 15.5 compare.py 역할

`compare.py`는 두 점수를 비교한다.

```text
Baseline Score
      VS
Candidate Score
```

예를 들어 허용 가능한 성능 하락을 5%p로 설정할 수 있다.

```text
Baseline: 100%
Candidate: 97%

Drop: 3%p

→ PASS
```

반대로 다음과 같다면 회귀로 판단한다.

```text
Baseline: 100%
Candidate: 60%

Drop: 40%p

→ Regression detected
→ FAIL
```

이를 기존 100% 점수와 비교하였다.

```text
Baseline Score : 100%
Candidate Score: 60%
Score Drop     : 40%
Allowed Drop   : 5%

Regression detected
```

---

## 15.6 CI에서 실패시키는 원리

비교 결과 허용 범위를 넘어서 성능이 하락하면 프로그램이 비정상 종료 코드를 반환한다.

```python
if drop > threshold:
    print("Regression detected")
    sys.exit(1)
```

`exit code 1`이 반환되면 GitHub Actions에서 해당 Step을 실패로 처리할 수 있다.

```text
Prompt Regression Test
        ↓
Score Drop > Threshold
        ↓
exit(1)
        ↓
GitHub Actions
        ↓
CI FAIL
```

```text
        ↓

        ↓

        ↓

        ↓
┌──────────────────┐
│ 하락 <= 기준     │ → PASS
│ 하락 > 기준      │ → FAIL
└──────────────────┘
```

# 16. 데모를 통해 얻은 점

프롬프트는 단순한 텍스트가 아니다.

프롬프트가 변경되면 모델의 실제 동작과 성능도 달라질 수 있다.

따라서 프롬프트도 코드와 마찬가지로 다음과 같은 관리가 필요하다.

```text
Versioning
+
Evaluation
+
Regression Test
+
CI
+
Deployment
+
Rollback
```

이 데모를 통해 얻을 수 있는 핵심 메시지는 다음과 같다.

> LLM 서비스에서도 프롬프트 변경은 코드 변경처럼 테스트하고 검증해야 한다.

그리고 골든셋 기반 회귀 테스트를 CI에 연결하면 프롬프트 변경으로 인한 성능 저하를 실제 배포 이전에 자동으로 탐지할 수 있다.

# 17. 전체 LLM Evaluation & Operations Pipeline

지금까지 내용을 모두 연결하면 다음과 같은 구조가 된다.

```text
Golden Set
    ↓
Bucket / Slice 분석
    ↓
Prompt / Model
    ↓
Evaluation
    ↓
Regression Test
    ↓
CI
    ↓
Prompt Versioning
    ↓
Canary / A/B / Shadow
    ↓
Production
    ↓
Tracing
    ↓
User Feedback
    ↓
Failure Case
    ↓
Human Review
    ↓
Golden Set Update
    ↓
다시 Evaluation
```

즉 LLM 평가와 운영은 한 번으로 끝나는 작업이 아니라 지속적으로 반복되는 구조다.

# 18. 핵심 정리

| 개념 | 의미 |
|---|---|
| Golden Set | 정답 또는 기대 결과가 검증된 평가 데이터 집합 |
| Bucket | 평가 문제를 큰 분야나 능력 단위로 분류 |
| Slice | 특정 조건을 가진 데이터만 필터링하여 분석 |
| Regression Test | 변경 이후 기존 성능이 떨어졌는지 확인 |
| CI | 변경이 발생할 때 평가와 테스트를 자동 실행 |
| LLM-as-a-Judge | LLM을 이용해 다른 LLM의 답변을 평가 |
| Rubric | Judge가 사용할 명확한 채점 기준 |
| Prompt Versioning | 프롬프트 변경 이력을 버전별로 관리 |
| Canary | 일부 사용자에게 먼저 배포하여 안전성 확인 |
| A/B Test | 두 버전을 비교하여 더 좋은 버전을 선택 |
| Shadow | 새 버전을 사용자에게 노출하지 않고 실제 트래픽으로 검증 |
| Tracing | 요청 하나의 입력부터 출력까지 전체 실행 과정 추적 |
| Feedback Loop | 실제 사용자 실패 사례를 다시 평가셋에 반영 |

# Conclusion

LLM 애플리케이션을 안정적으로 운영하기 위해서는 단순히 성능이 좋은 모델을 선택하는 것만으로 충분하지 않다.

먼저 신뢰할 수 있는 골든셋을 구축하고 모델이나 프롬프트 변경 이후 회귀가 발생하지 않았는지 지속적으로 평가해야 한다.

주관적인 답변 품질 평가에는 LLM-as-a-Judge를 사용할 수 있지만 위치 편향, 길이 편향, 스타일 편향, 자기 선호 편향을 고려해야 한다.

프롬프트 역시 코드처럼 버전을 관리하고 Canary, A/B Test, Shadow 등의 전략을 이용하여 안전하게 배포해야 한다.

배포 이후에는 입력, 출력, 토큰, 비용, 지연시간을 트레이싱하고 실제 사용자 피드백을 평가셋으로 다시 회수해야 한다.

결국 LLM 서비스의 품질 개선 과정은 다음과 같은 반복 구조로 볼 수 있다.

```text
평가
 ↓
배포
 ↓
관찰
 ↓
피드백
 ↓
평가셋 개선
 ↓
재평가
```

이러한 반복적인 평가와 운영 구조를 구축해야 실제 사용자 환경에서 지속적으로 개선되는 LLM 애플리케이션을 만들 수 있다.
