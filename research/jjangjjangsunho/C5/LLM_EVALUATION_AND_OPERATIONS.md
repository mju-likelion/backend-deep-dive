LLM 평가와 운영: 골든셋부터 사용자 피드백 루프까지

LLM 기반 서비스를 개발할 때는 단순히 모델을 호출하고 응답을 반환하는 것만으로 충분하지 않다.
모델의 품질을 지속적으로 평가하고, 프롬프트 변경으로 기존 성능이 떨어지지 않는지 확인하며, 실제 운영 환경에서 발생하는 문제를 다시 평가 데이터로 반영하는 과정이 필요하다.

1. 골든셋이란

골든셋(Golden Set)은 정답이 검증된 평가용 문제와 정답의 집합이다.
LLM의 성능을 평가하기 위해서는 모델이 생성한 답변이 올바른지 판단할 기준이 필요하다. 이때 기준으로 사용하는 데이터가 골든셋이다.
예를 들어 다음과 같은 데이터가 있다.
문제: 대한민국의 수도는 어디인가?
정답: 서울
문제: 2 + 3 × 4의 값은 얼마인가?
정답: 14
단순히 문제만 모아 놓은 것이 아니라 사람이 검토하거나 신뢰할 수 있는 자료를 통해 정답이 확정되어 있어야 한다.
골든셋을 이용하면 다음과 같은 방식으로 모델을 평가할 수 있다.

실제 LLM 평가 도구에서도 데이터셋에 입력과 기대 출력을 저장하고, 여러 실행 결과를 비교하는 방식을 사용한다.

그림 1. Langfuse의 Dataset 실행 화면이다. 동일한 데이터셋을 대상으로 여러 실험 결과와 점수를 비교할 수 있다.

골든셋을 이용한 기본적인 평가 흐름은 다음과 같다.
Golden Set
    ↓
LLM에게 문제 입력
    ↓
모델 답변 생성
    ↓
Golden Answer와 비교
    ↓
점수 계산
예를 들어 골든셋이 100문항이고 모델이 90문항을 올바르게 답했다면 정확도를 90%로 계산할 수 있다.
2. 골든셋은 유지보수가 필요하다

골든셋은 한 번 만들고 끝나는 데이터가 아니다.
서비스 정책, 데이터, 사용자 질문 유형 등이 계속 변하기 때문에 골든셋 역시 지속적으로 관리해야 한다.
대표적인 유지보수 작업은 다음과 같다.
잘못된 정답 수정
애매한 문제 제거
중복 문제 제거
새롭게 발견된 실패 사례 추가
서비스 정책 변경에 따른 정답 변경
특정 문제 유형의 부족한 비율 보완
예를 들어 기존에는 회원 탈퇴 시 포인트가 유지되었지만 서비스 정책이 변경되어 포인트가 소멸하도록 바뀌었다면, 기존 골든셋의 정답도 수정해야 한다.
그러나 골든셋을 계속 수정하면 과거 모델과 현재 모델의 성능을 동일한 기준으로 비교하기 어려울 수 있다.
따라서 골든셋 역시 다음과 같이 버전을 관리하는 것이 좋다.
Golden Set v1.0
Golden Set v1.1
Golden Set v2.0
평가 결과를 기록할 때도 어떤 골든셋 버전을 사용했는지 함께 저장한다.
Model A
Golden Set: v1.2
Accuracy: 91.5%
3. 버킷과 슬라이스

전체 점수만으로는 모델이 어떤 영역에서 강하고 어떤 영역에서 약한지 파악하기 어렵다.
이를 해결하기 위해 버킷과 슬라이스를 사용한다.
3.1 버킷

버킷(Bucket)은 평가 문제를 큰 능력이나 분야별로 분류한 집합이다.
예를 들어 다음과 같이 구성할 수 있다.
버킷평가 내용
지식 QA	일반 지식과 사실 질문
코드 생성	프로그래밍 문제
수학·논리	계산 및 추론 문제
한국어 이해	문맥 이해 및 생성
전체 정확도가 90%라고 하더라도 버킷별 결과를 보면 다음과 같은 차이가 나타날 수 있다.
전체 정확도: 90%

지식 QA: 72%
코드 생성: 98%
수학·논리: 96%
한국어 이해: 94%
이를 통해 모델이 전체적으로는 높은 성능을 보이지만 지식 QA 영역에서는 상대적으로 성능이 낮다는 사실을 알 수 있다.
즉, 버킷은 모델이 어떤 능력을 잘하고 못하는지를 확인하기 위해 사용한다.
3.2 슬라이스

슬라이스(Slice)는 평가 데이터에서 특정 조건을 만족하는 데이터만 필터링하여 분석하는 방식이다.
예를 들어 다음과 같은 조건을 사용할 수 있다.
난이도 = 어려움
부정문 포함 = true
문제 길이 > 500자
프로그래밍 언어 = Java
전체 평가셋이 100문제이고 이 중 어려운 문제 25개만 선택한다면 다음과 같이 평가할 수 있다.
전체 정확도: 90%

난이도 = 어려움
→ 25문제
→ 정확도 67%
전체 점수에서는 발견하기 어려웠던 모델의 약점을 슬라이스 분석을 통해 확인할 수 있다.
따라서 다음과 같이 구분할 수 있다.
버킷은 "어떤 능력을 평가하는가"를 본다.
슬라이스는 "어떤 조건에서 성능이 달라지는가"를 본다.
4. 회귀 테스트

회귀 테스트(Regression Test)는 새로운 기능이나 변경 사항이 기존에 정상적으로 동작하던 부분을 망가뜨리지 않았는지 확인하는 테스트다.
LLM 서비스에서는 모델이나 프롬프트를 변경했을 때 기존 성능이 떨어지지 않았는지 확인하기 위해 사용한다.
예를 들어 기존 프롬프트의 성능이 다음과 같다고 가정한다.
Prompt v1

수학: 80점
코드: 90점
한국어: 95점
프롬프트를 수정한 결과가 다음과 같을 수 있다.
Prompt v2

수학: 95점
코드: 95점
한국어: 85점
전체 성능은 좋아졌지만 기존에 잘하던 한국어 영역의 성능이 떨어졌다.
이러한 현상을 회귀라고 한다.
회귀 테스트는 다음과 같이 진행한다.
기존 모델 또는 프롬프트
        ↓
Golden Set 평가
        ↓
모델 또는 프롬프트 수정
        ↓
동일한 Golden Set 평가
        ↓
이전 결과와 비교
        ↓
성능 저하 여부 확인
따라서 골든셋은 회귀 테스트를 수행하기 위한 중요한 기준 데이터가 된다.
5. 골든셋 기반 회귀 테스트를 CI에 넣는 방법

CI는 Continuous Integration의 약자로 지속적 통합을 의미한다.
개발자가 코드를 Push하거나 Pull Request를 생성할 때 자동으로 빌드와 테스트를 실행하여 문제가 없는지 확인한다.
일반적인 CI 과정은 다음과 같다. 

GitHub Actions에서는 각 Job의 실행 순서와 상태를 그래프로 확인할 수 있다. 

그림 2. GitHub Actions의 Workflow Graph 예시다. 빌드, 테스트, 배포 Job의 의존성과 상태를 한눈에 확인할 수 있다.

일반적인 CI 과정은 다음과 같다.
코드 Push 또는 PR 생성
        ↓
CI 실행
        ↓
Build
        ↓
Unit Test
        ↓
Integration Test
        ↓
결과 확인
LLM 서비스에서는 여기에 골든셋 기반 평가를 추가할 수 있다.
Pull Request
      ↓
CI 실행
      ↓
일반 테스트
      ↓
Golden Set 평가
      ↓
기존 버전과 비교
      ↓
회귀 여부 확인
      ↓
기준 통과 → Merge 허용
기준 실패 → CI 실패
예를 들어 다음과 같은 기준을 설정할 수 있다.
전체 정확도 >= 90%

기존 버전 대비
전체 점수 하락 <= 2%

중요 Bucket 점수 >= 85%
새 프롬프트의 결과가 다음과 같다고 가정한다.
기존 버전: 93%
새 버전:   92%
허용 가능한 감소 폭이 2%라면 CI를 통과시킬 수 있다.
반면 다음과 같다면 실패시킬 수 있다.
기존 버전: 93%
새 버전:   86%
이렇게 하면 프롬프트나 모델이 변경될 때마다 사람이 직접 모든 평가를 실행하지 않아도 자동으로 회귀를 탐지할 수 있다.
6. LLM-as-a-Judge

LLM-as-a-Judge는 LLM을 이용해 다른 LLM의 답변을 평가하는 방법이다.
예를 들어 ChatGPT와 Claude의 답변을 Gemini에게 평가하도록 할 수 있다.
질문
 │
 ├─ ChatGPT 답변
 │
 └─ Claude 답변
        ↓
    Gemini Judge
        ↓
   답변 품질 평가
정답이 명확한 객관식이나 계산 문제는 프로그램으로 평가하기 쉽지만, 글쓰기나 설명 품질과 같이 정답을 단순 비교하기 어려운 문제는 LLM Judge를 사용할 수 있다.
그러나 LLM Judge 역시 하나의 언어 모델이기 때문에 다양한 편향이 발생한다.
7. LLM-as-a-Judge의 편향

7.1 위치 편향

위치 편향(Position Bias)은 답변 내용과 관계없이 앞이나 뒤에 배치된 답변을 더 선호하는 현상이다.
예를 들어 다음과 같이 평가한다.
A: ChatGPT 답변
B: Claude 답변
Judge가 A를 선택했다고 해서 반드시 ChatGPT의 답변이 더 좋다고 단정할 수 없다.
다음 평가에서는 순서를 변경할 수 있다. 

다음 그림은 동일한 품질의 답변을 비교했을 때 Judge별로 첫 번째 위치를 선택하는 비율이 달라질 수 있음을 보여주는 예시다.

그림 3. LLM Judge의 위치 편향 예시다. 이상적인 경우 첫 번째와 두 번째 답변이 동일한 품질이라면 선택 비율이 약 50%에 가까워야 한다.

위치 편향을 줄이기 위해 다음과 같이 답변의 순서를 바꾸거나 무작위화하여 평가한다.
A: Claude 답변
B: ChatGPT 답변
두 평가에서도 동일한 모델이 선택된다면 결과의 신뢰도를 높일 수 있다.
따라서 위치 편향을 줄이기 위해 Pairwise 평가 시 답변 순서를 바꾸어 반복 평가한다.
7.2 길이 편향

길이 편향(Verbosity Bias)은 Judge가 더 길고 자세한 답변을 더 좋은 답변이라고 판단하는 현상이다.
예를 들어 다음 두 답변은 모두 정답일 수 있다.
A:
서울이다.
B:
대한민국의 수도는 서울특별시이다.
서울은 대한민국의 정치, 경제, 문화의 중심지이며...
평가 목표가 단순한 정답 여부라면 A와 B 모두 정답이어야 한다.
하지만 LLM Judge가 설명이 긴 B에 더 높은 점수를 줄 수 있다.
이를 줄이기 위해 Judge 프롬프트에 다음과 같은 평가 조건을 명시할 수 있다.
답변의 길이 자체는 평가 기준에 포함하지 않는다.
정확성과 요구사항 충족 여부를 중심으로 평가한다.
7.3 스타일 편향

Judge가 Markdown, 표, 단계별 설명 등 특정 표현 방식을 더 선호할 수 있다.
예를 들어 내용은 동일하지만 다음 답변이 더 보기 좋다는 이유만으로 더 높은 점수를 받을 수 있다.
## 정답

**14**

### 풀이

1. 곱셈을 먼저 수행한다.
2. 3 × 4 = 12이다.
3. 12 + 2 = 14이다.
평가 목표가 정답 여부라면 이러한 표현 형식은 점수에 큰 영향을 주면 안 된다.
따라서 평가 기준을 명확하게 정의해야 한다.
정확성: 70%
지시사항 준수: 20%
명확성: 10%

Markdown 사용 여부와 답변 길이는 평가하지 않는다.
7.4 자기 선호 편향

Judge가 자기 자신이나 자신과 유사한 모델이 생성한 답변을 더 선호할 가능성이 있다.
예를 들어 GPT 계열 모델을 Judge로 사용하면서 GPT 계열 답변과 다른 모델 답변을 비교하면 특정 표현이나 생성 스타일에 대한 선호가 영향을 줄 수 있다.
이를 줄이기 위해 하나의 Judge만 사용하는 대신 서로 다른 모델을 이용한다.
Judge 1: Gemini
Judge 2: Grok
Judge 3: 다른 모델
여러 Judge의 결과를 비교하거나 다수결을 이용하면 특정 Judge 하나의 편향이 최종 결과를 지배하는 것을 줄일 수 있다.
7.5 Judge 자체의 오류

Judge 역시 LLM이므로 잘못된 판단을 할 수 있다.
Candidate의 답변이 틀렸지만 매우 그럴듯하게 작성된 경우 Judge가 올바른 답변으로 평가할 수도 있다.
따라서 가능하다면 Judge에게 다음 정보를 제공하는 것이 좋다.
질문
+
Golden Answer
+
Candidate Answer
+
Evaluation Rubric
Golden Answer가 존재하면 Judge가 단순히 자신의 지식에만 의존하지 않고 기준 답변과 비교할 수 있다.
8. LLM-as-a-Judge 편향 보정 방법

대표적인 편향과 보정 방법은 다음과 같다.
문제보정 방법
위치 편향	A/B 답변 순서를 바꾸어 재평가한다.
길이 편향	답변 길이를 평가하지 않도록 Rubric에 명시한다.
스타일 편향	정확성 및 요구사항 중심의 명확한 평가 기준을 만든다.
자기 선호 편향	서로 다른 계열의 Judge를 사용한다.
Judge 오류	Golden Answer를 함께 제공한다.
Judge 간 불일치	여러 Judge의 결과를 비교한다.
애매한 평가	사람이 최종 검토한다.
가장 중요한 것은 하나의 Judge 결과를 절대적인 정답으로 취급하지 않는 것이다.
다음과 같은 구조를 사용할 수 있다.
Golden Set
    │
    ├─ Model A
    └─ Model B
         ↓
    Judge 1
    Judge 2
         ↓
    결과 비교
         ↓
답변 순서 변경 후 재평가
         ↓
그래도 불일치
         ↓
Human Review
9. 프롬프트 버저닝

프롬프트 버저닝(Prompt Versioning)은 프롬프트도 코드처럼 버전을 부여하고 변경 이력을 관리하는 것이다.
프롬프트는 작은 문장 하나가 변경되더라도 모델의 응답에 큰 영향을 줄 수 있다.
예를 들어 처음에는 다음과 같은 프롬프트를 사용한다고 가정한다.
Prompt v1.0

사용자의 질문에 친절하게 답변한다.
답변이 지나치게 길다는 문제가 발생하여 수정한다.
Prompt v1.1

사용자의 질문에 핵심만 간결하게 답변한다.
환각을 줄이기 위해 다시 수정할 수 있다.
Prompt v1.2

사용자의 질문에 핵심만 간결하게 답변한다.
확실하지 않은 정보는 추측하지 않는다.
이렇게 버전을 관리하면 어떤 변경으로 인해 성능이 좋아지거나 나빠졌는지 추적할 수 있다.
다음과 같은 정보를 함께 기록하는 것이 좋다.


그림 4. Langfuse Prompt Management 화면이다. 프롬프트 버전과 production 등의 라벨을 함께 관리할 수 있다.

항목예시
Prompt Version	v1.2
변경 내용	추측 금지 지시 추가
모델	Model A
Golden Set	v2.1
평가 점수	94%
배포 상태	Production
생성 날짜	2026-10-04
프롬프트 버저닝의 가장 큰 장점 중 하나는 문제가 발생했을 때 이전 버전으로 되돌릴 수 있다는 점이다.
Prompt v1.4
      ↓
문제 발생
      ↓
Rollback
      ↓
Prompt v1.3
10. 프롬프트 배포 전략

새로운 프롬프트를 만들었다고 해서 바로 모든 사용자에게 적용하는 것은 위험할 수 있다.
평가셋에서는 성능이 좋아졌지만 실제 사용자 환경에서는 예상하지 못한 문제가 발생할 수 있기 때문이다.
따라서 다양한 배포 전략을 사용할 수 있다.
10.1 전체 배포

새 프롬프트를 모든 사용자에게 바로 적용하는 방식이다.
Prompt v1
    ↓
Prompt v2

모든 사용자에게 적용
구현은 가장 간단하지만 문제가 발생했을 때 전체 사용자에게 영향을 줄 수 있다는 단점이 있다.
10.2 Canary 배포

Canary 배포는 새로운 프롬프트를 일부 사용자에게 먼저 적용한 후 점진적으로 확대하는 방식이다.
예를 들어 처음에는 다음과 같이 운영한다.
90% → Prompt v1
10% → Prompt v2
문제가 없다면 비율을 확대한다.
50% → Prompt v2

↓

100% → Prompt v2
Canary 배포의 목적은 새로운 버전이 실제 환경에서 안전하게 동작하는지 확인하는 것이다.
10.3 A/B 테스트

A/B 테스트는 두 프롬프트를 동시에 운영하여 어떤 프롬프트가 더 좋은지 비교하는 방식이다.
A 그룹
→ Prompt v1

B 그룹
→ Prompt v2
다음과 같은 지표를 비교할 수 있다.
지표Prompt v1Prompt v2
정답률	89%	94%
사용자 만족도	4.1	4.4
평균 응답시간	2.1초	2.4초
Canary와 A/B 테스트의 목적은 다르다.
Canary는 새로운 버전이 안전한지 확인한다.
A/B 테스트는 어떤 버전이 더 좋은지 비교한다.
10.4 Shadow 배포

Shadow 배포는 실제 사용자에게는 기존 버전의 답변만 보여주면서 새로운 프롬프트도 뒤에서 동시에 실행하는 방식이다.
사용자 질문
     │
     ├─ Prompt v1
     │      ↓
     │  사용자에게 응답
     │
     └─ Prompt v2
            ↓
        내부 평가용
사용자는 v2의 답변을 보지 않지만 실제 운영 환경의 입력을 이용하여 새 프롬프트의 성능을 검증할 수 있다.
안전하게 새로운 모델이나 프롬프트를 테스트할 수 있다는 장점이 있다.
11. 트레이싱

트레이싱(Tracing)은 하나의 AI 요청이 들어온 순간부터 최종 응답이 반환될 때까지의 전체 과정을 추적하고 기록하는 것이다.
예를 들어 사용자가 다음과 같이 질문한다고 가정한다.
"회원 탈퇴하면 포인트가 어떻게 되나요?"
서비스 내부에서는 다음과 같은 과정이 발생할 수 있다.
사용자 입력
    ↓
프롬프트 생성
    ↓
검색 또는 DB 조회
    ↓
LLM 호출
    ↓
답변 생성
    ↓
후처리
    ↓
사용자에게 반환
이 과정에서 발생하는 정보를 기록한다.
예를 들어 하나의 Trace에 다음과 같은 정보가 저장될 수 있다.


그림 5. Langfuse Trace 화면이다. 하나의 요청 안에서 어떤 LLM 호출이 발생했는지 확인할 수 있으며 입력, 출력, 지연시간, 토큰 등의 정보를 추적할 수 있다.

11.1 입력과 출력

입력은 모델에게 전달된 사용자 질문, 시스템 프롬프트, 검색 결과 등의 정보다.
출력은 모델이 생성한 최종 응답이다.
입력과 출력을 기록하면 잘못된 답변이 발생했을 때 당시 모델이 어떤 정보를 받았는지 확인할 수 있다.
11.2 토큰

LLM은 문자열 자체가 아니라 토큰(Token)을 기준으로 입력과 출력을 처리한다.
일반적으로 다음과 같이 나눌 수 있다.
Input Token
+
Output Token
=
Total Token
토큰 사용량이 증가하면 일반적으로 비용도 증가한다.
프롬프트 변경 이후 갑자기 토큰이 증가하는 경우도 확인할 수 있다.
Prompt v1.3
평균 1,200 tokens

Prompt v1.4
평균 4,800 tokens
이 경우 새 프롬프트가 불필요하게 길거나 모델이 지나치게 긴 답변을 생성하고 있는지 조사할 수 있다.
11.3 비용

API 기반 LLM은 사용하는 토큰 수에 따라 비용이 발생할 수 있다.
따라서 요청별, 사용자별, 기능별 비용을 추적하면 어떤 기능이 많은 비용을 소비하는지 파악할 수 있다.
전체 요청 평균 비용
$0.004

$0.006

일반 QA 평균 비용
$0.002
11.4 지연시간

지연시간(Latency)은 사용자 요청이 들어온 후 응답이 반환되기까지 걸리는 시간이다.
전체 지연시간만 기록하는 것보다 각 단계별 지연시간을 기록하면 병목을 찾기 쉽다.
총 응답 시간: 8.2초

검색:       0.8초
DB 조회:    0.3초
LLM 호출:   6.7초
후처리:     0.4초
이를 통해 전체 응답이 느린 이유가 LLM 호출 때문이라는 사실을 확인할 수 있다.
트레이싱은 결국 다음 질문에 답하기 위해 사용한다.
어떤 입력이 들어왔는가

어떤 모델이 사용되었는가
어떤 출력이 생성되었는가
토큰을 얼마나 사용했는가
비용이 얼마나 발생했는가
응답에 얼마나 시간이 걸렸는가
어느 과정에서 오류가 발생했는가
12. 사용자 피드백을 평가셋으로 회수하는 루프

LLM 서비스의 평가셋은 개발자가 처음 만든 데이터만으로 유지해서는 실제 사용 환경을 충분히 반영하기 어렵다.
실제 사용자들은 개발자가 예상하지 못한 방식으로 질문하기 때문이다.
예를 들어 개발자가 다음과 같은 질문을 평가셋에 넣었다고 가정한다.
환불 가능 기간은 며칠인가?
실제 사용자는 다음과 같이 질문할 수 있다.
어제 결제했는데 지금 취소하면 돈 다 돌려받을 수 있나요?
두 질문의 목적은 비슷하지만 표현 방식은 상당히 다르다.
따라서 실제 사용자 환경에서 발생한 실패 사례를 다시 평가셋에 반영해야 한다.


그림 7. 사용자 피드백을 특정 Trace의 점수와 연결한 예시다. 어떤 입력과 출력이 낮은 평가를 받았는지 추적할 수 있다.

신고

고객 문의

사용자:

12.2 피드백을 바로 골든셋에 넣으면 안 된다

사용자가 👎을 눌렀다고 해서 해당 데이터를 바로 골든셋에 추가해서는 안 된다.
사용자가 단순히 답변 스타일을 싫어했을 수도 있고, 사용자가 잘못된 정보를 알고 있을 수도 있기 때문이다.
따라서 다음과 같은 검증 과정이 필요하다.
사용자 피드백
      ↓

      ↓

      ↓

      ↓

      ↓

      ↓

      ↓
Golden Set 추가
즉 다음과 같이 구분해야 한다.
사용자 피드백은 평가셋 후보 데이터다.
검증과 정답 확정이 완료된 데이터가 골든셋이 된다.

15. 핵심 개념 요약

개념의미
Golden Set	정답이 검증된 평가 문제와 정답의 집합이다.
Bucket	문제를 큰 능력이나 분야 단위로 분류한다.
Slice	특정 조건을 가진 데이터만 필터링하여 평가한다.
Regression Test	변경 이후 기존 성능이 떨어지지 않았는지 확인한다.
CI	코드나 프롬프트 변경 시 테스트를 자동으로 수행한다.
LLM-as-a-Judge	LLM을 이용하여 다른 LLM의 답변을 평가한다.
Prompt Versioning	프롬프트의 변경 이력을 버전별로 관리한다.
Canary	일부 사용자에게 새로운 버전을 먼저 배포한다.
A/B Test	두 버전을 동시에 운영하여 성능을 비교한다.
Shadow	실제 사용자에게 노출하지 않고 새 버전을 뒤에서 실행한다.
Tracing	요청 하나의 입력부터 출력까지 전체 실행 과정을 추적한다.
Feedback Loop	실제 사용자 실패 사례를 검증하여 평가셋으로 다시 반영한다.
마무리

LLM 서비스를 안정적으로 운영하기 위해서는 단순히 좋은 모델을 선택하는 것만으로 충분하지 않다.
먼저 신뢰할 수 있는 골든셋을 구성하고, 버킷과 슬라이스를 이용하여 모델의 세부적인 성능을 분석해야 한다. 모델이나 프롬프트가 변경될 때는 골든셋 기반 회귀 테스트를 수행하고 이를 CI 과정에 포함하여 성능 저하를 자동으로 탐지할 수 있다.
주관적인 답변 품질을 평가하기 위해 LLM-as-a-Judge를 사용할 수 있지만 위치 편향, 길이 편향, 스타일 편향과 같은 문제를 고려해야 한다. 따라서 명확한 평가 기준, 답변 순서 변경, 여러 Judge 활용, Human Review 등을 함께 사용하는 것이 중요하다.
프롬프트 역시 코드처럼 버전을 관리하고 Canary, A/B Test, Shadow와 같은 배포 전략을 이용하여 안전하게 운영 환경에 적용해야 한다.
배포 이후에는 입력, 출력, 토큰, 비용, 지연시간 등을 트레이싱하고, 실제 사용자 피드백에서 발견된 실패 사례를 검증하여 다시 골든셋으로 회수해야 한다.
결국 LLM 평가와 운영은 다음과 같은 반복 과정으로 볼 수 있다.
평가
→ 배포
→ 관찰
→ 피드백 수집
→ 평가셋 개선
→ 다시 평가
이러한 반복 구조를 구축해야 실제 사용자 환경에서 지속적으로 개선되는 LLM 서비스를 만들 수 있다.
