# LLM 평가와 벤치마크의 함정

## MMLU부터 HumanEval, 데이터 오염, LLM-as-a-Judge, 자체 평가셋까지

LLM을 비교하다 보면 MMLU, HumanEval, KMMLU 같은 벤치마크 점수를 자주 보게 된다.

예를 들어 어떤 모델은 MMLU에서 90점 이상을 받고, 어떤 모델은 HumanEval에서 높은 코딩 성능을 기록한다.  
그런데 막상 실제로 사용해 보면 **벤치마크 점수가 높은 모델이 항상 더 좋게 느껴지는 것은 아니다.**

왜 이런 차이가 생길까?

이 글에서는 다음 내용을 정리한다.

- 주요 LLM 벤치마크가 무엇을 측정하는지
- 각 벤치마크가 측정하지 못하는 것은 무엇인지
- 데이터 오염이 왜 문제인지
- 리더보드 점수와 실사용 체감이 왜 다른지
- LLM-as-a-Judge의 대표적인 편향
- 모델 간 차이를 통계적으로 어떻게 해석해야 하는지
- 마지막으로 우리 서비스에 맞는 평가셋을 어떻게 만들어야 하는지

---

## 1. 벤치마크란?

벤치마크(Benchmark)는 여러 모델을 **같은 조건에서 비교하기 위한 공통 시험 기준**이다.

예를 들어 두 개의 LLM이 있다고 하자.

- 모델 A
- 모델 B

그냥 사용해 보고 "A가 더 똑똑한 것 같다"고 말하는 것은 주관적이다.  
그래서 같은 문제를 두 모델에 주고 정답률, 성공률, 선호도 등을 측정한다.

즉,

> **벤치마크 = 모델의 특정 능력을 비교하기 위한 표준화된 시험**

이라고 볼 수 있다.

다만 중요한 점이 하나 있다.

**하나의 벤치마크가 LLM의 모든 능력을 측정하는 것은 아니다.**

---

# 2. 주요 LLM 벤치마크

## 2.1 MMLU

MMLU는 **Massive Multitask Language Understanding**의 약자다.

다양한 분야의 객관식 문제를 통해 LLM의 지식과 문제 해결 능력을 평가한다.

대표적인 분야는 다음과 같다.

- 수학
- 물리
- 컴퓨터과학
- 역사
- 경제학
- 법학
- 의학
- 철학

예를 들어 다음과 같은 문제를 푸는 방식이다.

> TCP의 특징으로 가장 적절한 것은?
>
> A. 비연결형 프로토콜이다.  
> B. 신뢰성 있는 연결형 전송을 제공한다.  
> C. 브로드캐스트 전용 프로토콜이다.  
> D. 암호화를 기본 제공한다.

이런 문제를 여러 분야에서 풀게 한 뒤 정답률을 계산한다.

### MMLU가 잘 측정하는 것

- 다양한 분야의 기본 지식
- 객관식 문제 해결 능력
- 비교적 짧은 문맥에서의 추론
- 여러 분야를 폭넓게 다루는 능력

### MMLU가 잘 측정하지 못하는 것

- 실제 대화 능력
- 장문의 문서 이해
- 코딩 능력
- 도구 사용 능력
- 최신 정보 검색
- 여러 단계의 실제 업무 수행
- 긴 프로젝트 맥락 유지

즉 MMLU 점수가 높다고 해서 그 모델이 실제 업무에서도 항상 좋은 것은 아니다.

---

## 2.2 MMLU-Pro

MMLU-Pro는 기존 MMLU보다 더 어려운 문제를 제공하기 위해 만들어진 평가 방식이다.

기존 MMLU보다 선택지가 많고, 단순 암기보다 추론을 더 요구하는 문제가 많다.

예를 들어 다음과 같은 문제가 있을 수 있다.

> 어떤 알고리즘의 시간복잡도가 `O(n log n)`이다.  
> 입력 크기 `n`이 2배가 되면 실행 시간은 대략 어떻게 변하는가?

기존 실행량이

```text
n log n
```

이라면 입력이 `2n`이 되었을 때는

```text
2n log(2n)
```

이 된다.

따라서 비율은

```text
2 × log(2n) / log(n)
```

정도가 된다.

이처럼 MMLU-Pro는 단순히 지식을 기억하는 것보다 **문제의 조건을 이해하고 계산하는 능력**을 더 요구한다.

### MMLU-Pro가 잘 측정하는 것

- 복잡한 객관식 추론
- 전문 분야 지식
- 단순 암기 이상의 문제 해결

### MMLU-Pro가 잘 측정하지 못하는 것

- 실제 서비스 사용성
- 긴 작업 수행
- 소프트웨어 프로젝트 수정
- 대화 스타일
- 창의적 문제 해결
- 도구 활용 능력

---

## 2.3 HumanEval

HumanEval은 AI의 **코드 생성 능력**을 평가하는 대표적인 벤치마크다.

주로 함수 설명과 함수 시그니처를 주고, LLM이 코드를 완성하도록 한다.

예를 들어 다음과 같은 문제가 있다고 하자.

```python
def add(a, b):
    """
    두 정수를 더한 값을 반환하시오.
    """
```

모델이 다음처럼 코드를 작성하면 된다.

```python
def add(a, b):
    return a + b
```

이후 숨겨진 테스트 케이스를 실행해서 코드가 정상 동작하는지 확인한다.

HumanEval에서는 보통 `pass@1`이라는 지표가 자주 사용된다.

예를 들어

```text
HumanEval pass@1 = 90%
```

라면, 모델이 처음 생성한 코드가 테스트를 통과할 확률이 약 90%라는 의미로 볼 수 있다.

### HumanEval이 잘 측정하는 것

- 짧은 함수 구현
- 알고리즘 문제 해결
- 코드 생성 능력
- 테스트 케이스 통과 여부

### HumanEval이 잘 측정하지 못하는 것

실제 개발은 함수 하나만 구현하고 끝나는 경우가 거의 없다.

예를 들어 실제 Spring 프로젝트에서는 다음 과정이 필요할 수 있다.

```text
요구사항 이해
→ 프로젝트 구조 분석
→ 여러 파일 수정
→ DB 구조 확인
→ 테스트
→ 에러 원인 분석
→ 다시 수정
```

HumanEval은 이런 능력을 충분히 측정하지 못한다.

즉 HumanEval 점수가 높다고 해서 반드시 대규모 프로젝트 개발을 잘한다는 뜻은 아니다.

# 3. 한국어 LLM 벤치마크

한국어 능력을 평가하기 위한 벤치마크도 존재한다.

대표적으로 다음과 같은 것들이 있다.

## KLUE

KLUE는 한국어 자연어 이해 능력을 평가하는 벤치마크다.

대표적인 평가 항목은 다음과 같다.

- 문장 분류
- 개체명 인식
- 자연어 추론
- 질의응답
- 문장 관계 이해

즉 한국어 문장의 구조와 의미를 얼마나 잘 이해하는지 평가하는 데 초점이 있다.

---

## KoBEST

KoBEST는 한국어 언어모델의 이해와 추론 능력을 평가하기 위한 여러 과제로 구성된 벤치마크다.

단순한 문장 이해뿐 아니라 한국어 문맥에서의 추론 능력을 평가하는 데 활용된다.

---

## KMMLU

KMMLU는 MMLU와 비슷한 방식으로 **한국어 기반의 다양한 지식 문제를 평가하는 벤치마크**라고 이해하면 쉽다.

분야는 다음처럼 다양할 수 있다.

- 과학
- 수학
- 역사
- 사회
- 법
- 경제
- 전문 지식

따라서 간단히 비교하면 다음과 같다.

| 벤치마크 | 주요 평가 대상 |
|---|---|
| MMLU | 영어 중심의 다양한 분야 지식과 추론 |
| MMLU-Pro | 더 어려운 전문 지식과 추론 |
| HumanEval | 코드 생성 |
| KLUE | 한국어 자연어 이해 |
| KoBEST | 한국어 이해와 추론 |
| KMMLU | 한국어 기반 종합 지식 및 객관식 문제 해결 |

---

# 4. 벤치마크가 측정하지 못하는 것

LLM 벤치마크를 볼 때 가장 중요한 것은 **점수가 무엇을 의미하는지뿐만 아니라 무엇을 의미하지 않는지도 아는 것**이다.

대부분의 벤치마크는 다음과 같은 요소를 완벽하게 측정하지 못한다.

## 4.1 실제 사용성

객관식 문제를 잘 푸는 것과 사용자가 실제로 만족하는 것은 다르다.

예를 들어 어떤 모델은 어려운 수학 문제는 잘 풀지만 사용자의 질문 의도를 잘 파악하지 못할 수 있다.

반대로 벤치마크 점수는 조금 낮더라도 설명이 명확하고 지시사항을 잘 따르는 모델이 실제 사용에서는 더 편할 수 있다.

---

## 4.2 긴 작업 수행 능력

실제 업무는 단일 질문으로 끝나지 않는다.

예를 들어 개발 업무라면 다음처럼 여러 단계가 이어진다.

```text
요구사항 분석
→ 코드베이스 탐색
→ 구현
→ 테스트
→ 실패 원인 확인
→ 수정
→ 재테스트
```

하지만 많은 벤치마크는

```text
문제 하나 → 답변 하나
```

형태로 구성되어 있다.

따라서 실제 업무 능력과 차이가 발생할 수 있다.

---

## 4.3 최신 정보

MMLU를 잘 푼다고 해서 오늘 발표된 뉴스, 최신 라이브러리 버전, 새로운 정책 등을 알고 있다는 뜻은 아니다.

훈련 데이터 이후의 정보는 별도의 웹 검색이나 외부 도구가 필요할 수 있다.

---

## 4.4 환각

벤치마크 점수가 높다고 해서 환각이 없는 것도 아니다.

LLM은 모르는 정보를 그럴듯하게 만들어내는 경우가 있다.

특히 실제 서비스에서는

- 존재하지 않는 API
- 존재하지 않는 논문
- 잘못된 법률 정보
- 없는 지하철 노선
- 틀린 통계

등을 생성하는 것이 큰 문제가 될 수 있다.

---

# 5. 데이터 오염이란?

데이터 오염(Data Contamination)은 **평가에 사용되는 문제가 모델의 학습 데이터에 포함된 상황**을 의미한다.

쉽게 말하면 시험 문제가 미리 유출된 것과 비슷하다.

예를 들어 MMLU의 문제와 정답이 인터넷에 공개되어 있다고 하자.

모델이 학습 과정에서 그 문제를 이미 봤다면, 평가할 때 정답을 맞혀도 실제로 추론해서 맞힌 것인지 단순히 기억해서 맞힌 것인지 알기 어렵다.

비유하면 다음과 같다.

> 수능을 보기 전에 실제 수능 문제와 정답지를 이미 본 학생이 시험을 보는 것

이런 상황에서는 벤치마크 점수가 모델의 실제 능력보다 높게 나타날 수 있다.

---

## 데이터 오염을 줄이는 방법

대표적인 방법은 다음과 같다.

- 새로운 문제를 지속적으로 만든다.
- 비공개 테스트셋을 사용한다.
- 기존 문제를 변형한다.
- 학습 데이터와 평가 데이터를 분리한다.
- 공개된 문제만으로 모델 성능을 판단하지 않는다.

결국 중요한 것은 모델이 **문제를 외웠는지, 실제로 일반화해서 해결하는지** 구분하는 것이다.

---

# 6. 리더보드 점수와 실사용 체감의 괴리

LLM 리더보드를 보면 모델 간 점수가 매우 세밀하게 나뉜다.

예를 들어 다음과 같은 결과가 있을 수 있다.

| 모델 | 점수 |
|---|---:|
| A | 91.2 |
| B | 90.8 |
| C | 90.1 |

이 표만 보면 A가 가장 좋아 보인다.

하지만 실제로 사용하면 B가 더 좋게 느껴질 수도 있다.

왜 이런 차이가 생길까?

---

## 6.1 벤치마크는 특정 능력만 본다

MMLU는 지식과 객관식 추론을 중심으로 평가한다.

HumanEval은 함수 단위 코딩을 중심으로 평가한다.

하지만 실제 사용에서는 다음 요소들도 중요하다.

- 지시사항 준수
- 대화 맥락 유지
- 코드베이스 이해
- 도구 사용
- 오류 복구
- 답변 속도
- 설명의 명확성
- 환각 빈도
- 장황함 여부

따라서 리더보드 점수가 실제 체감과 정확히 일치하지 않는 것은 자연스럽다.

---

## 6.2 시험 성적과 실무 능력은 다르다

벤치마크를 시험 성적이라고 생각하면 이해하기 쉽다.

수학 시험을 잘 본 사람이 반드시 소프트웨어 개발을 잘하는 것은 아니다.

마찬가지로 MMLU 점수가 높은 모델이 반드시

- 코딩
- 문서 작성
- 프로젝트 분석
- 서비스 기획

등에서 모두 뛰어난 것은 아니다.

결론적으로 모델을 선택할 때는 **리더보드뿐 아니라 내가 실제로 하려는 작업에서 직접 비교하는 것이 중요하다.**

---

# 7. LLM-as-a-Judge란?

LLM-as-a-Judge는 사람이 직접 평가하지 않고 **다른 LLM을 심판으로 사용해 답변 품질을 평가하는 방식**이다.

예를 들어 사용자 질문 하나에 대해 모델 A와 모델 B가 각각 답변을 생성했다고 하자.

그 답변을 모델 C에게 보여주고 다음과 같이 요청한다.

```text
두 답변 중 정확성, 유용성, 명확성이 더 높은 답변을 선택하시오.
```

이렇게 하면 대량의 답변을 비교적 빠르게 평가할 수 있다.

하지만 문제가 있다.

LLM 심판도 완전히 객관적이지 않다.

대표적으로 다음과 같은 편향이 존재할 수 있다.

---

# 8. LLM-as-a-Judge의 대표적인 편향

## 8.1 위치 편향

위치 편향(Position Bias)은 **답변이 제시된 순서에 따라 평가가 달라지는 현상**이다.

예를 들어 처음에는 다음 순서로 평가했다고 하자.

```text
답변 A
답변 B
```

Judge가 A를 선택했다.

그런데 순서를 바꾸어

```text
답변 B
답변 A
```

로 평가했더니 B를 선택한다면 문제가 있다.

답변 내용이 아니라 **위치 자체가 평가에 영향을 준 것**이기 때문이다.

### 완화 방법

A/B 순서를 바꾸어 여러 번 평가한다.

예를 들어

```text
1차 평가: A → B
2차 평가: B → A
```

두 결과가 일치하는지 확인한다.

---

## 8.2 길이 편향

길이 편향(Verbosity Bias 또는 Length Bias)은 **더 긴 답변을 더 좋은 답변으로 판단하는 경향**이다.

예를 들어 질문이 다음과 같다고 하자.

> TCP와 UDP의 차이는?

### 답변 A

```text
TCP는 연결형이며 신뢰성 있는 전송을 제공한다.
UDP는 비연결형이며 오버헤드가 적고 빠르다.
```

### 답변 B

```text
TCP는 연결 설정, 재전송, 순서 보장, 흐름 제어 등의 기능을 제공하는
신뢰성 있는 프로토콜이다. 반면 UDP는 연결 설정 과정이 없기 때문에
오버헤드가 적으며 실시간 스트리밍과 같은 환경에서 활용된다.
따라서 사용 목적에 따라 적절한 프로토콜을 선택해야 한다.
```

두 답변 모두 맞는 내용일 수 있다.

하지만 LLM Judge가 단순히 더 길고 자세하다는 이유로 B를 선택할 가능성이 있다.

실제 사용자에게는 A가 더 적절할 수도 있다.

---

## 8.3 자기 선호 편향

Self-preference Bias는 심판 역할을 하는 모델이 **자신이 생성한 답변이나 자신과 비슷한 스타일의 답변을 선호하는 현상**이다.

예를 들어 모델 A가 Judge 역할을 하는데 평가 대상 중 하나도 모델 A가 생성한 답변이라고 하자.

이 경우 내용의 품질뿐 아니라

- 문체
- 표현 방식
- 답변 구조
- 자주 사용하는 단어

등이 자기 모델과 비슷하다는 이유로 높은 평가를 받을 가능성이 있다.

---

## LLM-as-a-Judge 편향을 줄이기 위한 방법

다음과 같은 방법을 함께 사용하는 것이 좋다.

- 답변 순서를 랜덤하게 변경한다.
- 같은 문제를 여러 번 평가한다.
- 평가 기준을 명확하게 작성한다.
- 정확성, 관련성, 간결성 등을 각각 분리해서 평가한다.
- 여러 Judge 모델을 사용한다.
- 중요한 평가에서는 사람 평가와 함께 확인한다.

결국 LLM Judge 역시 **절대적인 정답 채점기가 아니라 하나의 모델**이라는 점을 기억해야 한다.

---

# 9. 통계적으로 의미 있는 비교

리더보드에서 모델 A가 90.2점, 모델 B가 89.8점을 기록했다고 하자.

단순히 숫자만 보면 A가 더 좋아 보인다.

하지만 이 차이가 실제 성능 차이인지, 우연히 발생한 것인지 확인해야 한다.

여기서 중요한 개념이 **표본 수**와 **신뢰구간**이다.

---

## 9.1 표본 수

표본 수는 평가에 사용한 문제의 개수다.

예를 들어 두 모델의 정확도 차이가 5%라고 하자.

### 20문제

```text
모델 A: 18개 정답
모델 B: 17개 정답
```

90%와 85%지만 실제로는 한 문제 차이다.

한 문제만 결과가 달라져도 순위가 뒤집힐 수 있다.

### 10,000문제

```text
모델 A: 9,000개 정답
모델 B: 8,500개 정답
```

이번에는 500문제 차이다.

같은 5% 차이라도 훨씬 안정적인 결과라고 볼 수 있다.

즉 일반적으로

> **표본 수가 많을수록 평가 결과의 불확실성이 줄어든다.**

---

# 10. 신뢰구간

신뢰구간은 측정된 점수 주변에 어느 정도의 불확실성이 있는지를 보여준다.

예를 들어 다음과 같은 결과가 있다고 하자.

```text
모델 A
정확도: 82%
95% 신뢰구간: 79% ~ 85%

모델 B
정확도: 80%
95% 신뢰구간: 77% ~ 83%
```

A가 숫자상 2% 더 높다.

하지만 두 신뢰구간이 상당 부분 겹친다.

따라서 단순히

> "A가 무조건 더 뛰어나다."

라고 결론 내리기 어렵다.

특히 LLM은 확률적으로 답변을 생성하기 때문에 같은 질문에서도 실행마다 답변이 달라질 수 있다.

그래서 제대로 비교하려면 다음을 함께 고려해야 한다.

- 충분한 문제 수
- 여러 번의 반복 평가
- 평균 점수
- 분산
- 신뢰구간
- 필요하다면 통계 검정

---

## 점수 차이만 보면 안 되는 이유

예를 들어 리더보드가 다음과 같다고 하자.

| 모델 | 점수 |
|---|---:|
| A | 86.4 |
| B | 86.1 |
| C | 85.9 |

차이는 존재한다.

하지만 평가 오차가 ±1점 정도라면 실제로는 세 모델의 성능 차이가 명확하지 않을 수도 있다.

따라서

> **점수 차이 = 실제 성능 차이**

라고 바로 해석해서는 안 된다.

---

# 11. 우리 태스크용 평가셋을 만들어야 하는 이유

범용 벤치마크는 모델의 전반적인 능력을 확인하는 데는 좋다.

하지만 실제 서비스에서 가장 중요한 것은

> **우리 서비스에서 필요한 일을 얼마나 잘 수행하는가?**

이다.

예를 들어 지하철 기반 AI 서비스를 만든다고 하자.

서비스에서 필요한 기능이 다음과 같다고 가정해 보자.

- 여러 사람의 출발지를 기반으로 중간역 추천
- 자연어 조건 이해
- 환승 횟수 제한 반영
- 이동시간 비교
- 표지판 이미지 해석
- 경로 설명
- 존재하지 않는 역이나 노선 생성 방지

이 경우 MMLU 점수보다 이러한 문제를 직접 평가하는 것이 훨씬 의미 있다.

---

# 12. 우리 태스크용 평가셋 만드는 방법

## 12.1 실제 태스크를 기능별로 나눈다

먼저 LLM이 서비스에서 어떤 일을 하는지 분해한다.

예를 들어 중간역 추천 기능이라면 다음처럼 나눌 수 있다.

```text
사용자 입력 이해
→ 출발지 추출
→ 사용자 조건 추출
→ 외부 계산 결과 확인
→ 추천 후보 비교
→ 최종 답변 생성
```

각 단계마다 실패 가능성이 다르기 때문에 각각 평가할 수 있다.

---

## 12.2 실제 사용자 질문을 기반으로 문제를 만든다

평가셋은 실제 사용 환경과 최대한 비슷해야 한다.

예를 들어 다음과 같은 질문이 좋다.

```text
나는 홍대입구고 친구는 잠실인데
둘 다 40분 안쪽이면 좋겠고 가능하면 2호선이었으면 좋겠어.
```

이 질문에서 LLM은 다음 정보를 추출해야 한다.

```text
출발지 1: 홍대입구
출발지 2: 잠실
최대 이동시간: 40분
선호 노선: 2호선
```

이렇게 실제 사용자 표현을 평가하는 것이 중요하다.

---

## 12.3 일반 케이스와 엣지 케이스를 섞는다

쉬운 문제만으로 평가하면 실제 서비스 성능을 제대로 알 수 없다.

### 일반 케이스

```text
강남역과 홍대입구역 사이에서 만나기 좋은 곳 추천해줘.
```

### 애매한 케이스

```text
적당히 가운데인데 놀 것도 많았으면 좋겠어.
```

### 엣지 케이스

```text
한 명은 서울역이고 한 명은 수원역인데
환승은 최대 1번까지만 가능해.
```

실제 서비스에서는 이런 엣지 케이스에서 문제가 발생할 가능성이 높다.

---

## 12.4 정답 기준을 명확하게 만든다

평가셋에서 가장 중요한 부분이다.

예를 들어 다음 질문은 평가하기 어렵다.

```text
가장 좋은 중간역을 추천해라.
```

"좋다"의 기준이 없기 때문이다.

대신 다음과 같이 정의할 수 있다.

```text
각 사용자의 이동시간 차이가 10분 이내이며,
최대 이동시간이 가장 짧은 역을 추천한다.
```

이렇게 하면 평가 기준이 명확해진다.

---

## 12.5 반드시 포함해야 할 내용과 금지할 내용을 정의한다

정답 문장을 하나로 고정할 필요는 없다.

예를 들어 다음처럼 평가할 수 있다.

```text
필수 포함
- 추천역: 사당역
- A 예상 이동시간: 28~32분
- B 예상 이동시간: 25~30분

금지
- 존재하지 않는 지하철 노선 언급
- 계산 결과와 다른 이동시간 제시
- 사용자 조건 무시
```

이렇게 하면 표현은 달라도 내용이 맞는 답변을 정답으로 처리할 수 있다.

---

# 13. 평가 기준을 여러 개로 나누기

LLM 답변은 단순 정답/오답으로만 평가하기 어려운 경우가 많다.

따라서 여러 평가 항목으로 나누는 것이 좋다.

| 평가 항목 | 의미 |
|---|---|
| 정확성 | 사실이나 계산 결과가 맞는가 |
| 조건 준수 | 사용자의 요구사항을 반영했는가 |
| 관련성 | 질문과 관련된 답변을 했는가 |
| 환각 | 존재하지 않는 정보를 만들지 않았는가 |
| 설명 품질 | 사용자가 이해하기 쉽게 설명했는가 |

예를 들어 한 답변의 결과를 다음처럼 기록할 수 있다.

```text
정확성: 1
조건 준수: 1
관련성: 1
환각 없음: 0
설명 품질: 1
```

이런 방식이면 모델의 구체적인 약점을 찾기 쉽다.

---

# 14. 실제 실패 사례를 평가셋에 계속 추가하기

좋은 평가셋은 한 번 만들고 끝나는 것이 아니다.

서비스를 운영하다 보면 예상하지 못했던 실패 사례가 계속 나온다.

예를 들어 다음과 같은 문제가 발생했다고 하자.

```text
사용자: 환승 없이 갈 수 있는 곳만 추천해줘.

LLM:
환승 1회가 필요한 경로를 추천함.
```

이 사례는 바로 새로운 평가 문제로 추가할 수 있다.

이후 모델이나 프롬프트를 수정한 뒤 다시 테스트한다.

```text
서비스 실패
→ 평가셋 추가
→ 모델/프롬프트 수정
→ 다시 평가
```

이러한 방식은 소프트웨어 테스트의 **회귀 테스트(Regression Test)** 와 비슷하다.

---

# 15. 개발셋과 테스트셋 분리하기

자체 평가셋을 만들 때도 데이터 오염과 비슷한 문제가 생길 수 있다.

같은 평가 문제를 계속 보면서 프롬프트를 수정하면 결국 그 문제에만 맞게 최적화될 수 있다.

따라서 평가셋을 나누는 것이 좋다.

### 개발셋(Dev Set)

프롬프트를 수정하거나 모델을 개선할 때 반복적으로 사용한다.

### 테스트셋(Test Set)

최종 성능을 평가할 때 사용한다.

가능하다면 테스트셋은 개발 과정에서 자주 보지 않는 것이 좋다.

시험으로 비유하면

```text
개발셋 = 연습문제
테스트셋 = 실제 시험
```

이라고 볼 수 있다.

---

# 16. 평가 데이터 예시

실제로는 JSON 형태로 평가셋을 관리할 수도 있다.

```json
{
  "id": "midpoint_001",
  "input": {
    "users": [
      "홍대입구",
      "잠실"
    ],
    "request": "둘 다 40분 안에 갈 수 있고 2호선이면 좋겠어"
  },
  "expected": {
    "max_travel_time": 40,
    "preferred_line": "2호선"
  },
  "criteria": {
    "constraint_understanding": true,
    "no_hallucination": true,
    "recommendation_supported": true
  }
}
```

처음부터 수천 개를 만들 필요는 없다.

작은 서비스라면 우선 **실제 사용 패턴을 잘 반영한 수십~수백 개의 평가 문제**를 만드는 것만으로도 상당히 유용하다.

문제 수보다 중요한 것은 다음이다.

- 실제 사용자 입력을 반영했는가?
- 실패하기 쉬운 케이스가 들어 있는가?
- 평가 기준이 명확한가?
- 서비스에서 중요한 기능을 골고루 포함하는가?

---

# 17. 결국 어떤 벤치마크를 믿어야 할까?

벤치마크는 모델 비교에서 매우 유용하다.

하지만 하나의 숫자로 모델 전체 성능을 판단하면 안 된다.

예를 들어

```text
MMLU → 지식과 객관식 추론
HumanEval → 짧은 코드 생성
KLUE → 한국어 이해
KMMLU → 한국어 지식과 문제 해결
```

처럼 각 벤치마크는 서로 다른 능력을 측정한다.

또한 벤치마크 결과에는 다음과 같은 문제가 있을 수 있다.

- 데이터 오염
- 특정 문제 형식에 대한 과적합
- LLM Judge 편향
- 작은 표본으로 인한 불확실성
- 실제 서비스 환경과의 차이

따라서 모델을 평가할 때는

```text
범용 벤치마크
+
실제 사용자 테스트
+
우리 서비스용 평가셋
```

을 함께 보는 것이 가장 좋다.

---

# 마무리

LLM 벤치마크 점수는 모델을 이해하는 좋은 출발점이다.

하지만 중요한 것은 **점수 자체보다 그 점수가 무엇을 측정했는지 이해하는 것**이다.

MMLU 점수가 높다고 모든 일을 잘하는 것은 아니며, HumanEval 점수가 높다고 실제 프로젝트 개발까지 잘하는 것도 아니다.

특히 실제 서비스를 개발한다면 가장 중요한 것은 결국 다음 질문이다.

> **"이 모델이 우리 서비스에서 실제로 발생하는 문제를 얼마나 잘 해결하는가?"**

그래서 범용 벤치마크를 참고하되, 실제 사용자 데이터를 기반으로 자체 평가셋을 만드는 것이 중요하다.

좋은 평가셋은 다음 요소를 갖는다.

```text
실제 사용자 입력
+ 명확한 정답 기준
+ 일반 케이스
+ 엣지 케이스
+ 실제 실패 사례
+ 충분한 표본 수
```

결국 LLM 평가에서 중요한 것은 단순히 **누가 리더보드 1등인가**가 아니라,

**내가 해결하려는 문제에서 어떤 모델이 가장 안정적으로 좋은 결과를 내는가**

를 확인하는 것이다.
