# LLM 평가와 벤치마크의 함정

> MMLU, HumanEval부터 LLM-as-a-Judge와 자체 평가셋까지

- 실험 대상: **ChatGPT GPT-5.6 Sol (High)**, **Claude Sonnet 5 (높음)**
- Judge: **Gemini**, **Grok**
- 평가셋 생성 보조: **Perplexity**
- 총 문항 수: **50문항**

---

## 1. 벤치마크란?

벤치마크(Benchmark)는 여러 AI 모델을 **같은 조건에서 비교하기 위한 표준화된 평가 기준**이다.

모델을 몇 번 사용해 본 뒤 “이 모델이 더 똑똑한 것 같다”라고 판단하면 개인적인 체감에 크게 의존하게 된다.  
그래서 같은 문제를 여러 모델에 입력하고 정답률, 성공률, 선호도 등의 지표를 이용해 비교한다.

> **벤치마크 = AI의 특정 능력을 일정한 조건에서 측정하기 위한 시험**

다만 하나의 벤치마크가 LLM의 모든 능력을 측정하는 것은 아니다.  
각 벤치마크가 **무엇을 잘 측정하고, 무엇을 놓치는지** 함께 보는 것이 중요하다.

---

## 2. 주요 LLM 벤치마크

### 2.1 MMLU

MMLU(Massive Multitask Language Understanding)는 수학, 과학, 역사, 법학, 경제학, 컴퓨터과학 등 다양한 분야의 객관식 문제를 이용해 모델의 지식과 문제 해결 능력을 평가한다.

### MMLU가 잘 측정하는 것

- 다양한 분야의 지식
- 객관식 문제 해결 능력
- 비교적 짧은 문맥에서의 추론
- 여러 분야를 폭넓게 다루는 능력

### MMLU가 잘 측정하지 못하는 것

- 실제 대화 능력
- 장문의 문서 이해
- 코딩 능력
- 도구 사용 능력
- 최신 정보 검색
- 여러 단계의 실제 업무 수행
- 긴 프로젝트 맥락 유지

즉 MMLU 점수가 높다고 해서 해당 모델이 실제 업무에서도 항상 좋은 것은 아니다.

---

### 2.2 MMLU-Pro

MMLU-Pro는 기존 MMLU보다 더 어려운 문제를 제공하기 위해 만들어진 벤치마크다.

기존 MMLU보다 선택지가 많고, 단순 암기보다는 여러 조건을 종합하여 답을 도출하는 추론 능력을 더 많이 요구한다.

### MMLU-Pro가 잘 측정하는 것

- 복잡한 객관식 추론
- 전문 분야 지식
- 단순 암기 이상의 문제 해결

### MMLU-Pro가 잘 측정하지 못하는 것

- 실제 서비스 사용성
- 긴 작업 수행
- 소프트웨어 프로젝트 수정
- 대화 스타일
- 창의적인 문제 해결
- 외부 도구 활용 능력

---

### 2.3 HumanEval

HumanEval은 LLM의 **코드 생성 능력**을 평가하는 대표적인 벤치마크다.

예를 들어 다음과 같이 함수 설명과 함수 시그니처를 제공한다.

```python
def add(a, b):
    """
    두 정수를 더한 값을 반환하시오.
    """
```

모델이 다음과 같이 코드를 작성하면,

```python
def add(a, b):
    return a + b
```

미리 준비된 테스트 케이스를 실행하여 정상적으로 동작하는지 확인한다.

HumanEval에서는 `pass@1`이라는 지표가 자주 사용된다.

```text
HumanEval pass@1 = 90%
```

이는 모델이 처음 생성한 코드가 테스트를 통과하는 비율을 의미한다.

### HumanEval이 잘 측정하는 것

- 짧은 함수 구현
- 알고리즘 문제 해결
- 코드 생성 능력
- 테스트 케이스 통과 여부

### HumanEval이 잘 측정하지 못하는 것

실제 개발은 함수 하나만 구현하고 끝나는 경우가 거의 없다.

예를 들어 실제 프로젝트에서는 다음과 같은 과정이 필요하다.

```text
요구사항 이해
→ 프로젝트 구조 분석
→ 여러 파일 수정
→ DB 구조 확인
→ 테스트
→ 에러 원인 분석
→ 다시 수정
```

따라서 HumanEval 점수가 높다고 해서 실제 대규모 프로젝트 개발 능력이 그대로 보장되는 것은 아니다.

## 3. 한국어 LLM 벤치마크

한국어 능력을 평가하기 위한 벤치마크도 존재한다.

### KLUE

KLUE는 한국어 자연어 이해 능력을 평가하는 벤치마크다.

대표적인 평가 항목은 다음과 같다.

- 문장 분류
- 개체명 인식
- 자연어 추론
- 질의응답
- 문장 관계 이해

즉 한국어 문장의 구조와 의미를 얼마나 잘 이해하는지 평가하는 데 초점을 둔다.

### KoBEST

KoBEST는 한국어 언어모델의 이해와 추론 능력을 평가하기 위한 여러 과제로 구성된 벤치마크다.

단순한 문장 이해뿐 아니라 한국어 문맥에서의 추론 능력을 평가한다.

### KMMLU

KMMLU는 MMLU와 비슷한 방식으로 **한국어 기반의 다양한 지식 문제를 평가하는 벤치마크**다.

다양한 전문 지식과 한국어 환경에서의 문제 해결 능력을 평가한다.

| 벤치마크 | 주요 평가 대상 |
|---|---|
| MMLU | 다양한 분야의 지식과 추론 |
| MMLU-Pro | 더 어려운 전문 지식과 추론 |
| HumanEval | 코드 생성 |
| KLUE | 한국어 자연어 이해 |
| KoBEST | 한국어 이해 및 추론 |
| KMMLU | 한국어 기반 종합 지식 및 문제 해결 |

## 4. 벤치마크가 측정하지 못하는 것

LLM 벤치마크를 볼 때 중요한 것은 **점수가 무엇을 의미하는지뿐만 아니라 무엇을 의미하지 않는지도 확인하는 것**이다.

실제 LLM 사용에서는 다음과 같은 요소도 중요하다.

- 사용자의 지시를 제대로 따르는가
- 이전 대화의 맥락을 유지하는가
- 긴 코드나 문서를 이해하는가
- 필요한 도구를 적절하게 사용하는가
- 오류가 발생했을 때 수정할 수 있는가
- 존재하지 않는 정보를 생성하지 않는가
- 설명이 이해하기 쉬운가
- 불필요하게 장황하지 않은가

즉,

> **벤치마크 점수 ≠ 실제 사용 경험**

이라고 볼 수 있다.

## 5. 데이터 오염

데이터 오염(Data Contamination)은 **평가에 사용하는 문제가 모델의 학습 데이터에 이미 포함되어 있는 상황**을 의미한다.

쉽게 말하면,

> 시험을 보기 전에 시험 문제와 정답을 미리 본 상황

과 비슷하다.

공개된 벤치마크 문제를 모델이 학습 과정에서 이미 접했다면 모델이 문제를 맞혀도 다음 두 상황을 구분하기 어렵다.

```text
실제로 추론해서 맞힌 것
vs
학습 과정에서 본 문제를 기억해서 맞힌 것
```

따라서 공개 벤치마크 점수만으로 모델의 실제 추론 능력과 일반화 능력을 판단할 때는 주의가 필요하다.

### 데이터 오염을 줄이는 방법

- 새로운 문제를 지속적으로 만든다.
- 비공개 테스트셋을 사용한다.
- 기존 문제를 변형한다.
- 학습 데이터와 평가 데이터를 분리한다.
- 공개된 문제만으로 모델 성능을 판단하지 않는다.

결국 중요한 것은 모델이 **문제를 외웠는지, 실제로 일반화해서 해결했는지**를 구분하는 것이다.

## 6. 리더보드 점수와 실사용 체감의 괴리

예를 들어 리더보드 결과가 다음과 같다고 하자.

| 모델 | 점수 |
|---|---:|
| A | 91.2 |
| B | 90.8 |
| C | 90.1 |

숫자만 보면 A의 점수가 가장 높다.

하지만 실제 사용에서는 B가 더 편하게 느껴질 수도 있다.

벤치마크에서 충분히 측정하지 않는 다음 요소들이 실사용에 큰 영향을 주기 때문이다.

- 지시사항 준수
- 대화 맥락 유지
- 코드베이스 이해
- 도구 사용
- 오류 복구
- 환각
- 답변 속도
- 설명의 명확성
- 장황함 여부

따라서 모델을 선택할 때는 리더보드뿐 아니라 **내가 실제로 수행하려는 작업에서 직접 비교하는 과정**도 중요하다.

## 7. LLM-as-a-Judge

LLM-as-a-Judge는 사람이 모든 답변을 직접 평가하는 대신 **다른 LLM을 평가자(Judge)로 사용하는 방식**이다.

예를 들어 같은 질문에 모델 A와 모델 B가 답했다고 하자.

두 답변을 다른 LLM에게 입력하고 다음과 같이 요청할 수 있다.

```text
두 답변을 정확성, 논리성, 질문 충족 여부를 기준으로 평가하시오.
```

이 방식을 이용하면 많은 답변을 비교적 빠르게 평가할 수 있다.

하지만 Judge 역시 LLM이기 때문에 완전히 객관적인 채점기라고 볼 수는 없다.

---

## 8. LLM-as-a-Judge의 대표적인 편향

### 8.1 위치 편향(Position Bias)

답변의 내용이 아니라 **답변이 제시되는 순서에 따라 평가가 달라지는 현상**이다.

예를 들어,

```text
답변 A
답변 B
```

순서에서는 A를 선택했지만,

```text
답변 B
답변 A
```

로 순서를 변경했을 때 B를 선택한다면 위치 편향이 발생했을 가능성이 있다.

이를 줄이기 위해서는 A/B 순서를 뒤집어 다시 평가하거나 여러 번 평가하는 방법을 사용할 수 있다.

---

### 8.2 길이 편향(Verbosity Bias)

더 긴 답변을 더 좋은 답변으로 판단하는 경향이다.

두 답변의 정확도가 비슷하더라도 길고 자세한 답변이 더 전문적으로 보일 수 있다.

하지만 사용자가 간결한 답변을 원했다면 짧고 정확한 답변이 더 적절할 수도 있다.

---

### 8.3 자기 선호 편향(Self-preference Bias)

Judge 모델이 자신이 주로 생성하는 문체나 답변 구조와 비슷한 답변을 더 선호할 수 있는 현상이다.

따라서 하나의 Judge 결과만 사용하는 것보다 **여러 Judge를 사용하여 결과가 일관적인지 확인하는 것**이 중요하다.

### LLM-as-a-Judge 편향을 줄이는 방법

- 답변 순서를 변경하여 평가한다.
- 같은 문제를 여러 번 평가한다.
- 평가 기준을 명확하게 작성한다.
- 정확성, 관련성, 간결성 등을 따로 평가한다.
- 여러 Judge 모델을 사용한다.
- 중요한 평가에서는 사람 평가를 함께 활용한다.


```text
Gemini
Grok
```

```text
Perplexity
```

```text
LLM 종합평가셋 - 문제 (답안 없음, 50문제).json
```

## 10. Judge에 따라 결과가 달라졌다

전체 평가 결과는 다음과 같다.

| 모델 | Gemini Judge | Grok Judge |
|---|---:|---:|
| ChatGPT GPT-5.6 Sol (High) | 100 | 82 |
| Claude Sonnet 5 | 90 | 90 |

Gemini가 Judge일 때는

```text
ChatGPT: 100
Claude: 90
```

으로 평가됐다.

반면 Grok이 Judge일 때는

```text
ChatGPT: 82
Claude: 90
```

으로 평가됐다.

즉 **동일한 모델의 동일한 답변을 평가했지만 Judge를 변경하자 결과가 달라졌다.**

특히 ChatGPT는 Judge에 따라

```text
100 → 82
```

로 **18%p의 차이**가 발생했다.

반면 Claude는 Gemini와 Grok 모두 90점으로 평가됐다.

이 결과는 LLM-as-a-Judge를 사용할 때 **어떤 Judge 모델을 사용했는가가 평가 결과에 영향을 줄 수 있다는 점**을 보여준다.

## 11. 어떤 문제에서 판정이 달라졌을까?

오답 판정이 한 번이라도 발생한 문항은 다음과 같다.

| 문제 | 영역 | 세부 분야 | ChatGPT / Gemini | ChatGPT / Grok | Claude / Gemini | Claude / Grok |
|---|---|---|---:|---:|---:|---:|
| Q5 | 한국어 지식 QA | 한국문화 | ✅ | ❌ | ❌ | ❌ |
| Q6 | 한국어 지식 QA | 한국역사 | ✅ | ❌ | ✅ | ✅ |
| Q8 | 한국어 지식 QA | 한국사회 | ✅ | ❌ | ❌ | ❌ |
| Q10 | 한국어 지식 QA | 한국지리 | ✅ | ❌ | ❌ | ❌ |
| Q11 | 한국어 지식 QA | 한국교육 | ✅ | ❌ | ✅ | ✅ |
| Q12 | 한국어 지식 QA | 한국역사 | ✅ | ❌ | ❌ | ❌ |
| Q15 | 한국어 지식 QA | 한국경제 | ✅ | ❌ | ✅ | ✅ |
| Q48 | 한국어 이해·생성 | 높임법 | ✅ | ❌ | ❌ | ❌ |
| Q50 | 한국어 이해·생성 | 비유적 표현 | ✅ | ❌ | ✅ | ✅ |

- ✅ = 해당 Judge가 정답으로 판정
- ❌ = 해당 Judge가 오답으로 판정

Claude는 두 Judge 모두 다음 문제를 오답으로 판정했다.

```text
Q5
Q8
Q10
Q12
Q48
```

반면 ChatGPT는 Gemini에서는 50문항 전체를 정답으로 판정받았지만, Grok에서는 총 9문항을 오답으로 판정받았다.

## 12. 영역별 결과

| 영역 | ChatGPT / Gemini | ChatGPT / Grok | Claude / Gemini | Claude / Grok |
|---|---:|---:|---:|---:|
| 한국어 지식 QA | 15/15 | 8/15 | 11/15 | 11/15 |
| 코드 생성 | 12/12 | 12/12 | 12/12 | 12/12 |
| 수학·논리 추론 | 12/12 | 12/12 | 12/12 | 12/12 |
| 한국어 이해·생성 | 11/11 | 9/11 | 10/11 | 10/11 |

코드 생성과 수학·논리 추론 영역에서는 두 Judge의 판정 차이가 발생하지 않았다.

반면 Judge 간 차이는 주로 다음 영역에서 나타났다.

- 한국어 지식 QA
- 한국어 이해·생성

특히 ChatGPT의 한국어 지식 QA는

```text
Gemini: 15/15
Grok: 8/15
```

로 큰 차이가 발생했다.

이번 실험에서는 코드나 수학처럼 비교적 정답을 명확하게 검증할 수 있는 문제보다 **지식의 정확성이나 언어 해석이 필요한 문제에서 Judge 간 차이가 더 크게 나타났다.**

---

## 13. 평가셋 자체도 검증해야 한다

실험을 진행하면서 Judge뿐 아니라 **평가셋의 문제와 정답 자체도 검증해야 한다는 점**을 확인할 수 있었다.

평가 문제의 정답 기준이 잘못되어 있거나 문제가 모호하다면 다음 세 상황을 구분하기 어렵다.

```text
Judge가 잘못 평가한 것
vs
모델이 실제로 틀린 것
vs
평가셋의 정답이 잘못된 것
```

즉 LLM 평가에는 다음 세 요소가 동시에 영향을 준다.

```text
모델의 실제 성능
+
Judge의 평가 성향
+
평가셋의 품질
```

Perplexity와 같은 AI 도구를 사용하면 평가 문제를 빠르게 제작할 수 있다는 장점이 있다.

하지만 AI가 생성한 문제와 정답 역시 사람이 다시 확인하는 검증 과정이 필요하다.

---

## 14. 통계적으로 의미 있는 비교

평가 결과가

```text
ChatGPT: 100
Claude: 90
```

이라고 해서 10점의 차이가 모델 전체의 절대적인 성능 차이라고 바로 판단할 수는 없다.

이번 평가셋은 총 50문항이기 때문에 **한 문제의 비중이 2%p**다.

```text
50/50 = 100%
45/50 = 90%
41/50 = 82%
```

즉 몇 문제의 판정이 바뀌는 것만으로도 전체 점수가 크게 달라질 수 있다.

### 표본 수

예를 들어 모델 간 정확도 차이가 5%라고 하더라도 문제 수가 20개라면 실제로는 한 문제 차이에 불과할 수 있다.

```text
모델 A: 18/20 = 90%
모델 B: 17/20 = 85%
```

반면 10,000문제를 평가한다면 같은 5% 차이라도 훨씬 많은 문제의 결과가 누적된 것이다.

```text
모델 A: 9,000/10,000
모델 B: 8,500/10,000
```

따라서 일반적으로 **표본 수가 많을수록 평가 결과의 불확실성이 줄어든다.**

### 신뢰구간

예를 들어 다음과 같은 결과가 있다고 하자.

```text
모델 A
정확도: 82%
95% 신뢰구간: 79% ~ 85%

모델 B
정확도: 80%
95% 신뢰구간: 77% ~ 83%
```

A의 점수가 2%p 높지만 두 신뢰구간은 상당 부분 겹친다.

따라서 단순히 숫자만 보고

```text
A가 무조건 더 뛰어나다.
```

라고 결론 내리기 어렵다.

더 신뢰도 높은 비교를 위해서는 다음 요소를 함께 고려해야 한다.

- 평가 문항 수 확대
- 동일 조건에서 반복 평가
- 여러 Judge 사용
- 평균 점수
- 분산
- 신뢰구간
- 필요한 경우 통계적 검정

## 15. 우리 태스크용 평가셋은 어떻게 만들까?

범용 벤치마크는 모델의 전반적인 능력을 확인하는 데 유용하다.

하지만 실제 서비스를 개발할 때 더 중요한 것은 다음 질문이다.

> **우리 서비스에서 필요한 작업을 얼마나 잘 수행하는가?**

예를 들어 지하철 기반 AI 서비스를 만든다고 하면 다음과 같은 능력이 필요할 수 있다.

- 여러 사람의 출발지를 기반으로 중간역 추천
- 자연어 조건 이해
- 환승 횟수 제한 반영
- 이동시간 비교
- 표지판 이미지 해석
- 경로 설명
- 존재하지 않는 역이나 노선 생성 방지

따라서 MMLU 점수만 확인하는 것보다 이러한 문제를 직접 평가하는 것이 더 의미 있을 수 있다.

### 실제 태스크를 기능별로 나누기

```text
사용자 입력 이해
→ 출발지 추출
→ 사용자 조건 추출
→ 외부 계산 결과 확인
→ 추천 후보 비교
→ 최종 답변 생성
```

각 단계마다 발생할 수 있는 오류가 다르기 때문에 단계별 평가가 가능하다.

### 실제 사용자 질문을 평가 문제로 사용하기

예를 들어 다음과 같은 질문을 사용할 수 있다.

```text
나는 홍대입구고 친구는 잠실인데
둘 다 40분 안쪽이면 좋겠고 가능하면 2호선이었으면 좋겠어.
```

모델은 다음 조건을 올바르게 추출해야 한다.

```text
출발지 1: 홍대입구
출발지 2: 잠실
최대 이동시간: 40분
선호 노선: 2호선
```

### 일반 케이스와 엣지 케이스를 함께 사용하기

#### 일반 케이스

```text
강남역과 홍대입구역 사이에서 만나기 좋은 곳 추천해줘.
```

#### 애매한 케이스

```text
적당히 가운데인데 놀 것도 많았으면 좋겠어.
```

#### 엣지 케이스

```text
한 명은 서울역이고 한 명은 수원역인데
환승은 최대 1번까지만 가능해.
```

실제 서비스에서는 이런 엣지 케이스에서 문제가 발생할 가능성이 높다.

---

## 16. 실제 실패 사례를 평가셋에 추가하기

좋은 평가셋은 한 번 만들고 끝나는 것이 아니다.

서비스를 운영하면서 발생한 실제 실패 사례를 계속 평가셋에 추가할 수 있다.

예를 들어,

```text
사용자:
환승 없이 갈 수 있는 곳만 추천해줘.

LLM:
환승 1회가 필요한 경로를 추천함.
```

이라는 문제가 발생했다면 이 사례를 새로운 평가 문제로 추가한다.

그 후 프롬프트나 모델을 수정한 뒤 다시 테스트한다.

```text
서비스 실패
→ 평가셋 추가
→ 모델/프롬프트 수정
→ 다시 평가
```

이러한 방식은 소프트웨어 개발의 **회귀 테스트(Regression Test)** 와 비슷하게 활용할 수 있다.

---

## 17. 개발셋과 테스트셋 분리

자체 평가셋을 만들 때도 데이터 오염과 비슷한 문제가 발생할 수 있다.

같은 평가 문제를 계속 확인하면서 프롬프트를 수정하면 결국 해당 문제에만 맞게 최적화될 수 있다.

따라서 평가셋을 개발셋과 테스트셋으로 나누는 것이 좋다.

### 개발셋(Dev Set)

프롬프트를 수정하거나 모델을 개선할 때 반복적으로 사용한다.

### 테스트셋(Test Set)

최종 성능을 평가할 때 사용한다.

시험으로 비유하면 다음과 같다.

```text
Dev Set = 연습문제
Test Set = 실제 시험
```

가능하면 테스트셋은 개발 과정에서 자주 확인하지 않는 것이 좋다.

---

## 18. 결론

LLM 벤치마크는 모델을 비교하기 위한 매우 유용한 도구다.

하지만 하나의 점수만 보고 모델 전체의 성능을 판단하기는 어렵다.

이번 50문항 자체 평가에서도 동일한 모델의 동일한 답변을 평가했지만 Judge에 따라 결과가 달라졌다.

| 모델 | Gemini | Grok |
|---|---:|---:|
| ChatGPT GPT-5.6 Sol (High) | 100 | 82 |
| Claude Sonnet 5 | 90 | 90 |

또한 모든 영역에서 Judge 간 차이가 발생한 것은 아니다.

코드 생성과 수학·논리 영역에서는 결과가 동일했지만, 한국어 지식 QA와 한국어 이해·생성 영역에서는 판정 차이가 발생했다.

Perplexity를 활용하면 평가셋 제작 시간을 줄일 수 있었지만, AI가 생성한 문제와 정답 자체도 검증해야 한다는 문제도 있었다.

따라서 LLM을 평가할 때는 다음 요소를 함께 고려하는 것이 중요하다.

```text
범용 벤치마크
+
우리 태스크용 평가셋
+
여러 Judge
+
문항별·영역별 분석
+
평가셋 정답 검증
+
통계적 불확실성 확인
```

결국 중요한 것은 단순히 리더보드에서 누가 높은 점수를 받았는지가 아니다.

> 어떤 문제로 평가했는가?  
> 누가 평가했는가?  
> 어느 영역에서 결과가 달라졌는가?  
> 정답 기준은 믿을 만한가?  
> Judge를 바꿔도 결과가 유지되는가?

그리고 최종적으로 확인해야 할 것은 다음이다.

> **내가 해결하려는 문제에서 어떤 모델이 가장 안정적으로 좋은 결과를 내는가?**
