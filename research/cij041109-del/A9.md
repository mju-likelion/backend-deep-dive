## 한 줄 요약

예외는 "어떻게 잡느냐"보다 **Spring 안에서 어떻게 흘러가고, 클라이언트에게 어떤 모양으로 도착해야 하느냐**가 중요하다.
실패했는데 `200 OK`로 응답하거나 내부 예외 메시지를 그대로 내보내는 대신, **올바른 HTTP 상태 코드 + 바뀌지 않는 에러 코드 + 표준 형식(RFC 9457)**으로 응답한다.

## 도입 (슬라이드 1–3)

### 문제 상황: 200 OK인데, 실패했습니다 (슬라이드 2)

이미 가입된 이메일로 다시 가입 요청을 보냈을 때, 안티패턴 코드(`BadMemberController`)는 이런 응답을 낸다.

```
HTTP/1.1 200 OK
Content-Type: application/json

{ "success": false, "data": null, "message": "…SQL 문장과 테이블 이름…" }
```

| 영역 | 비용 |
|---|---|
| 프론트엔드 | `fetch`의 `response.ok`는 2xx면 true라서 HTTP 수준에서 실패를 알 수 없다. 모든 화면에서 body의 `success`를 한 번 더 확인해야 한다. |
| 모니터링 | 운영 대시보드는 보통 4xx, 5xx 비율을 본다. 전부 200이면 장애가 나도 그래프가 평온하다. |
| 보안 | 테이블 이름, 제약조건 이름 같은 내부 정보가 그대로 나간다. |

> 화면의 message 문구는 축약한 예시이며, 실제 문구는 DB와 Hibernate 버전에 따라 다르다.

## PART 1 · Java 예외 기초 (슬라이드 4–7)

### Java 예외의 기본 구조 (슬라이드 4)

```
Throwable
├── Error                      (OutOfMemoryError, StackOverflowError — 잡지 않는다)
└── Exception
    ├── IOException, SQLException …      ← 체크 예외
    └── RuntimeException                 ← 언체크 예외
        └── IllegalArgumentException, DataAccessException(Spring) …
```

- `RuntimeException`은 `Exception`의 자식이지만 **규칙은 정반대**다. `Exception`을 상속하면 컴파일러가 `catch` 또는 `throws`를 강제하고, `RuntimeException`을 상속하면 강제하지 않는다.
- 체크 여부는 **컴파일 타임 규칙**일 뿐이다. JVM 입장에서는 던지고 잡는 동작과 비용이 같다. "언체크가 더 가볍다"는 말은 틀렸다.
- 언체크 예외도 `catch`할 수 있다. 강제하지 않을 뿐이다.

출처: Oracle Java Tutorials — The Catch or Specify Requirement

### 체크 예외 vs 언체크 예외 (슬라이드 5)

| 구분 | 체크 예외 (`Exception` 계열) | 언체크 예외 (`RuntimeException` 계열) |
|---|---|---|
| 컴파일러 | `catch` 또는 `throws` 선언 강제 | 강제하지 않음 |
| 장점 | 실패 가능성이 메서드 시그니처에 드러남 | 코드 간결, 람다/스트림 친화, 계층 간 결합 감소 |
| 단점 | `throws`가 상위 계층까지 번짐, 의미 없는 `catch` 유발 | 문서화하지 않으면 실패 가능성을 놓치기 쉬움 |
| `@Transactional` 기본 | **롤백하지 않음 (커밋)** | **롤백** |
| 대표 예 | `IOException`, `SQLException` | `IllegalArgumentException`, `DataAccessException` |

- **Java 공식 가이드의 기준**: 호출자가 합리적으로 복구할 수 있으면 체크, 복구할 방법이 없으면 언체크.
- **웹 API 실무에서의 해석**: 요청 처리 중 비즈니스 오류는 "이 요청을 실패시키고 응답을 잘 주는 것"이 복구다. 그래서 언체크로 던지고 전역에서 처리한다. Spring이 JDBC의 체크 예외(`SQLException`)를 언체크(`DataAccessException`)로 바꿔 주는 것도 같은 철학이다.

출처: dev.java — Unchecked Exceptions: The Controversy / Spring Framework Reference — Rolling Back a Declarative Transaction

### 함정: 체크 예외는 기본 설정에서 롤백되지 않는다 (슬라이드 6)

```java
@Transactional
public void saveThenThrowChecked(String email) throws ExternalApiException {
    memberRepository.save(new Member(email, "checked"));
    throw new ExternalApiException("외부 API 실패");
}                                   // → 커밋된다!

@Transactional(rollbackFor = ExternalApiException.class)
public void saveThenThrowCheckedWithRollbackFor(String email)
        throws ExternalApiException { ... }   // → 롤백
```

| 경우 | 기대 결과 |
|---|---|
| 체크 예외 | 데이터 남음 (커밋) |
| 언체크 예외 | 롤백 |
| 체크 예외 + `rollbackFor` | 롤백 |

> 위 결과는 **공식 문서 기준 예상**이다. `TransactionRollbackTest`로 확인하며, 실행 결과는 [demo/README.md](./demo/README.md)의 기록표에 채운다.

**추가 함정**: 예외를 `catch`해서 삼키면 언체크여도 커밋된다. 트랜잭션 프록시는 **메서드 밖으로 나온 예외**만 보기 때문이다. 잡고 다시 던지면(rethrow) 롤백된다.

출처: Spring Framework Reference — Rolling Back a Declarative Transaction

### 흔한 오해 4가지 (슬라이드 7)

| 오해 | 실제 |
|---|---|
| 예외는 일단 다 catch해야 안전하다 | 처리할 수 없는 곳에서 잡으면 정보만 사라진다. 잡는 곳은 "의미 있게 처리할 수 있는 한 곳". |
| 커스텀 예외는 많을수록 좋다 | 클라이언트 분기나 처리 방식이 달라지는 단위로만 만든다. |
| `e.getMessage()`를 응답에 주면 친절하다 | 내부 구현이 노출된다. 메시지는 사용자용, 스택트레이스는 로그용으로 분리한다. |
| `@ControllerAdvice`가 모든 예외를 잡는다 | 필터(Spring Security 등)처럼 `DispatcherServlet` 밖에서 난 예외는 거치지 않는다. |

출처: Spring Framework Reference — Controller Advice / RFC 9457

## PART 2 · 예외의 비용 (슬라이드 8–10)

### 비용은 대부분 '생성' 시점의 스택트레이스다 (슬라이드 8)

| 단계 | 하는 일 |
|---|---|
| 1. `new IllegalArgumentException()` | 객체 생성 |
| 2. `fillInStackTrace()` | **현재 콜 스택 전체를 기록 — 깊을수록 비쌈** (생성 시점에 일어난다) |
| 3. `throw` → 스택 되감기 → `catch` | 핸들러를 찾을 때까지 프레임을 거슬러 올라감 |
| 4. `getStackTrace()` / 로그 출력 | `StackTraceElement[]` 변환, 문자열화 |

`Throwable`의 생성자는 `fillInStackTrace()`를 호출하고, `writableStackTrace=false`로 만들면 호출하지 않는다.

```java
// ❌ 예상 가능한 결과를 예외로 표현
try {
    member = repo.findByEmail(email).orElseThrow();
} catch (NoSuchElementException e) {
    member = createGuest();
}

// ✅ 정상 흐름은 조건 분기 / Optional로
Member member = repo.findByEmail(email).orElseGet(this::createGuest);
```

**결론**: 예상 가능한 결과는 반환값으로, 계약 위반이나 진짜 예외 상황만 예외로 쓴다. 이유는 **성능보다 먼저 가독성과 의도**다. 예외를 보면 읽는 사람은 "뭔가 잘못됐다"고 읽는다. 성능은 두 번째 이유이며 숫자로 확인해야 한다.

출처: Java SE 21 API — `java.lang.Throwable`

### 데모 D: JMH 벤치마크 설계 (슬라이드 9)

"무엇을 분리해서 재는가"가 핵심이다.

| 벤치마크 | 하는 일 | 포함되는 비용 |
|---|---|---|
| `branch` | `if`로 실패를 표현 (예외 없음) | 없음 (기준선) |
| `createOnly` | 예외를 만들기만 하고 던지지 않음 | 생성 + 스택 기록 |
| `throwWithStackTrace` | 일반 예외 생성 + throw + catch | 생성 + 스택 기록 + throw/catch |
| `throwNoStackTrace` | 스택트레이스를 끈 예외 throw + catch | 생성 + throw/catch |
| `throwPreallocated` | 미리 만든 예외를 재사용해 throw + catch | throw/catch만 |

- `depth`(콜 스택 깊이): 1 / 32 / 128. 실제 Spring 요청은 Tomcat, 필터, `DispatcherServlet`, 프록시를 거쳐 콜 스택이 깊다. 데모 앱의 `/demo/stack-depth`로 컨트롤러 시점의 실제 프레임 수를 볼 수 있다.
- `Blackhole.consume`: 결과가 쓰이지 않으면 JIT 컴파일러가 코드를 통째로 제거할 수 있어서, 결과를 "쓰는 척"해 이를 막는다.
- 측정 조건: 워밍업 5회 × 1초, 측정 10회 × 1초, Fork 3(JVM을 3번 새로 띄움), `-prof gc`로 연산당 할당량(B/op), 모드 `AverageTime`(ns/op). 측정한 PC 환경(CPU, OS, JDK)을 함께 기록한다.

출처: OpenJDK JMH

### 측정 결과: 실측 예정 (슬라이드 10)

**결과 표의 숫자는 측정 전이라 모두 "실측 예정"이다.** 작성 환경에서는 JMH를 실행하지 못했고, 측정하지 않은 숫자를 채우지 않는다.

이미 확인한 것은 벤치마크 코드가 만드는 예외의 **스택 프레임 수**뿐이다 (시간 측정 아님).

| depth | 기록된 스택 프레임 수 |
|---|---|
| 1 | 4 |
| 32 | 35 |
| 128 | 131 |
| (스택트레이스를 끈 예외) | 0 |

깊이에 비례해 기록량이 늘어난다는 것까지만 확인했고, 실행 시간 차이는 측정이 필요하다. 결과가 나오면 절대값 대신 "branch 대비 몇 배"로 해석하고, 오차 범위가 겹치면 차이가 있다고 말하지 않는다. 실행 방법과 기록표는 [demo/README.md](./demo/README.md)의 "3단계 — JMH 벤치마크"에 있다.

> 참고(심화): HotSpot의 `OmitStackTraceInFastThrow` 최적화 때문에, JIT 컴파일된 코드에서 `NullPointerException` 같은 암묵적 예외가 반복되면 스택트레이스 없는 예외를 재사용하기도 한다. 운영 로그에 스택트레이스 없는 NPE가 찍히는 이유다.

## PART 3 · Spring MVC 내부 동작 (슬라이드 11–13)

### 던져진 예외는 HandlerExceptionResolver 체인을 탄다 (슬라이드 11)

```
요청 → 필터 → DispatcherServlet → Controller → Service → Repository
                     ▲                                │
                     └────── 예외가 호출 스택을 거슬러 올라옴 ──┘
```

`DispatcherServlet`이 예외를 `HandlerExceptionResolver` 체인에 넘긴다. 기본 3개이며, **앞에서부터 물어보고 처음 처리한 곳에서 멈춘다.**

| 순서 | Resolver | 처리 대상 |
|---|---|---|
| 1 | `ExceptionHandlerExceptionResolver` | `@ExceptionHandler`. **컨트롤러 안의 로컬 핸들러를 먼저**, 없으면 `@ControllerAdvice`를 `@Order` 순서로 |
| 2 | `ResponseStatusExceptionResolver` | `@ResponseStatus`가 붙은 예외, `ResponseStatusException` |
| 3 | `DefaultHandlerExceptionResolver` | 405, 415 같은 Spring MVC 표준 예외 |

- 아무도 처리하지 못하면 예외는 서블릿 컨테이너까지 올라가고, `/error`로 포워드되어 Spring Boot의 `BasicErrorController`가 기본 에러 응답을 만든다.
- **필터는 `DispatcherServlet` 바깥**이다. 그래서 Spring Security 필터에서 난 예외는 이 체인을 타지 않고, `AuthenticationEntryPoint`(401) / `AccessDeniedHandler`(403)로 따로 처리해야 한다.
- 참고: Spring Boot는 `DefaultErrorAttributes`를 체인 맨 앞에 끼워 넣는다. 예외를 요청 속성에 **기록만 하고** 다음으로 넘기며, 나중에 `/error`에서 이 정보를 쓴다.

출처: Spring Framework Reference — Web MVC › Exceptions / Controller Advice

### 계층마다 책임이 다르고, 예외는 경계에서 '번역'된다 (슬라이드 12)

| 계층 | 책임 | 예외에 대해 |
|---|---|---|
| Controller | HTTP 입출력, `@Valid` 검증 | 예외를 **잡지 않는다** → Advice에 위임 |
| Service | 비즈니스 규칙, 트랜잭션 | 도메인 예외를 던지고, 하위 예외를 **의미 있는 예외로 변환** |
| Repository | 데이터 접근 | `SQLException`·JPA 예외를 Spring이 `DataAccessException`으로 **자동 변환** |
| 전역 Advice | 예외 → HTTP 응답 | `@RestControllerAdvice`가 상태 코드 + 에러 코드 + `ProblemDetail`로 번역 |

중복 이메일 가입 시 예외의 여행:

```
SQLException                        ← JDBC 드라이버
 → DataIntegrityViolationException  ← Spring 변환
 → DuplicateEmailException          ← Service 변환 (원본은 cause로 보존)
 → 409 + MEMBER_DUPLICATE_EMAIL     ← Advice 변환
```

**왜 번역하는가**: ① 상위 계층이 JDBC/JPA를 몰라도 되게, ② 기술적 사실에 비즈니스 의미를 부여, ③ `cause`로 원본 정보를 보존.

출처: Spring Framework Reference — DAO Support / 데모 코드 `member/MemberService.java`

### 잘못된 처리 vs 개선된 설계 (슬라이드 13)

**Before — Controller** (설명용 나쁜 예. 데모의 실제 Controller에는 이 try-catch가 없다)

```java
@PostMapping
public ResponseEntity<?> create(@RequestBody MemberCreateRequest req) {
    try {
        var body = service.register(req);
        return ResponseEntity.ok(body);
    } catch (DataIntegrityViolationException e) {   // Controller가 DB 기술을 안다
        return ResponseEntity.status(409)
                .body(e.getMessage());                // 노출
    }
}
```

**After — Service** (데모 코드 `member/MemberService.java`)

```java
@Transactional
public MemberResponse register(MemberCreateRequest req) {
    if (memberRepository.existsByEmail(req.email())) {
        throw new DuplicateEmailException();               // 분기
    }
    try {
        Member saved = memberRepository.saveAndFlush(
                new Member(req.email(), req.name()));
        return MemberResponse.from(saved);
    } catch (DataIntegrityViolationException e) {          // 경합
        throw new DuplicateEmailException(e);              // cause
    }
}
```

| Before의 문제 3가지 | After로 바꾸면 |
|---|---|
| ① Controller가 DB 예외 이름을 안다 | ① Controller는 DB를 몰라도 된다 (try-catch 제거) |
| ② `e.getMessage()` 그대로 노출 (테이블·SQL) | ② 응답은 안전한 메시지만, 원본은 `cause` → 서버 로그 |
| ③ DB 규칙 위반이면 이유 불문 409 — 뜻이 부정확 | ③ '이메일 중복'이라는 정확한 이름 + 에러 코드, 응답 통일 |

- `existsByEmail`은 예상 가능한 상황을 분기로 먼저 처리한다. 그래도 `catch`가 있는 이유는 **동시 가입(경합)**이다. 두 요청이 모두 확인을 통과하면 DB의 유니크 제약이 마지막 방어선이 되어 예외를 낸다. 이를 같은 `DuplicateEmailException`으로 바꾸고 원본을 `cause`로 넘긴다.
- `saveAndFlush`를 쓰는 이유: `save`만 하면 INSERT가 커밋 시점까지 미뤄져 예외가 `try` 밖에서 날 수 있다. `flush`로 이 자리에서 SQL을 실행시켜 예외를 받는다.
- `catch`에서 원래 예외는 끝나고, **새 예외를 던진다.** 던졌으므로 트랜잭션도 롤백된다. (삼켰다면 커밋된다.)
- 한계: 이 `catch`는 DB 규칙 위반이면 모두 이메일 중복으로 바꾼다. 입력 검증(`@Valid`)을 앞에서 하므로 이 맥락에서는 합리적이고, 더 엄밀하게는 제약조건 이름까지 확인한다.

결과적으로 **Controller에는 try-catch가 없고, 정상 경로만 남는다. 실패는 Advice가 한 곳에서 HTTP로 번역한다.**

## PART 4 · 데모 B: @RestControllerAdvice (슬라이드 14–15)

### 예외 → 응답 번역을 한 곳에 (슬라이드 14)

```java
@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ProblemDetail> handleBusiness(
            BusinessException ex, HttpServletRequest req) {
        ErrorCode code = ex.getErrorCode();
        return ResponseEntity.status(code.status())
            .body(toProblem(code, ex.getMessage(), req.getRequestURI()));
    }

    @ExceptionHandler(Exception.class)          // 최후의 안전망
    public ResponseEntity<ProblemDetail> handleUnexpected(
            Exception ex, HttpServletRequest req) {
        log.error("[unexpected] uri={}", req.getRequestURI(), ex);
        return ...COMMON_INTERNAL_ERROR...;     // 일반 메시지
    }
}
```

- `@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`. 반환값이 메시지 컨버터로 body에 쓰인다. 요청을 받는 클래스가 아니라 **컨트롤러들의 예외를 대신 받는 공통 클래스**다.
- `ResponseEntityExceptionHandler`를 상속하면 405, 415, 검증 실패 등 Spring MVC 예외도 `ProblemDetail`로 응답한다.
- `BusinessException` 핸들러는 예외 안의 `ErrorCode`에서 상태 코드와 에러 코드를 꺼내므로, 새 비즈니스 예외를 추가해도 핸들러를 고칠 필요가 없다.
- `Exception` 핸들러(안전망)는 스택트레이스를 **로그에만** 남기고 응답에는 일반 메시지만 보낸다.
- 애플리케이션 시작 시 `ExceptionHandlerExceptionResolver`가 Advice 빈을 찾아 등록한다.

출처: Spring Framework Reference — Controller Advice / Error Responses

### 핸들러가 여러 개 매칭되면? 우선순위 3가지 규칙 (슬라이드 15)

| # | 규칙 | 검증 엔드포인트 | 예상 |
|---|---|---|---|
| 1 | **컨트롤러 로컬 `@ExceptionHandler`가 전역 Advice보다 먼저.** 로컬이 있으면 Advice는 보지도 않는다. | `GET /priority/local` | `controller-local` |
| 2 | **한 클래스 안에서는 던져진 타입에 가장 가까운 핸들러.** `ExceptionDepthComparator`, root 매칭이 cause 매칭보다 우선. | `GET /priority/depth` | `BusinessException` 핸들러 → 404 |
| 3 | **여러 Advice는 `@Order` 순서로 하나씩 검사.** 높은 순위 Advice의 cause 매칭이 낮은 순위 Advice의 root 매칭을 이긴다. | `GET /priority/order` | `advice-order1-cause-match` |

규칙 3 설명: 던진 예외(root)는 `IllegalStateException`이고 그 안에 `CustomCauseException`(cause)이 담겨 있다. `@Order(1)` Advice는 cause만, `@Order(2)` Advice는 root와 정확히 맞는다. Spring은 **Order 1 Advice를 root와 cause 모두 먼저 확인**하므로 Order 1이 이긴다.

> 위 "예상"은 공식 문서 기준 기대값이며, `DemoB_ExceptionHandlerPriorityTest`(MockMvc) 실행 결과는 [demo/README.md](./demo/README.md)의 기록표에 채운다.

**Tip**: 순서에 기대는 Advice가 여럿이면 `@Order`를 반드시 명시한다. 가장 확실한 해법은 **Advice를 하나로 유지**하는 것이다.

출처: Spring Framework Reference — `@ExceptionHandler`

## PART 5 · 에러 응답 설계 (슬라이드 16–20)

### 같은 실패, 다른 응답: 200 OK vs 404 Problem Details (슬라이드 16, 데모 A)

```
# Before — GET /bad/members/999999
HTTP/1.1 200 OK
Content-Type: application/json
{ "success": false, "data": null, "message": "id=999999 회원이 존재하지 않습니다." }

# After — GET /api/members/999999
HTTP/1.1 404 Not Found
Content-Type: application/problem+json
{
  "type": "https://api.example.com/problems/member-not-found",
  "title": "회원을 찾을 수 없습니다.",
  "status": 404,
  "detail": "id=999999 회원이 존재하지 않습니다.",
  "instance": "/api/members/999999",
  "code": "MEMBER_NOT_FOUND"
}
```

| 항목 | Before → After |
|---|---|
| HTTP 상태 | 항상 200 → 404 / 409 / 400 / 500 |
| 분기 기준 | `message` 문자열 → 불변 `code` |
| 예상 못 한 오류 | 내부 메시지 노출 → 일반 메시지 + 서버 로그 |

After 응답이 만들어지는 과정: Service가 `MemberNotFoundException`(안에 `ErrorCode.MEMBER_NOT_FOUND`)을 던지고 → Controller는 아무것도 하지 않고 → 예외가 `DispatcherServlet`까지 올라와 → 1번 Resolver가 Advice의 `BusinessException` 핸들러를 찾아 → `ErrorCode`에서 404와 코드를 꺼내 `ProblemDetail`로 응답한다.

> 응답은 코드 기준 **예상 형태**이며 필드 순서는 다를 수 있다. `DemoA_BadVsGoodResponseTest`가 상태 코드, Content-Type, `code`, `instance` 값을 검증한다.

### RFC 9457 Problem Details: 에러 응답에도 표준이 있다 (슬라이드 17)

**왜 등장했나**: HTTP 상태 코드만으로는 오류를 충분히 설명할 수 없다. API마다 에러 포맷을 새로 만들면 클라이언트는 API마다 따로 배워야 한다. → 기계가 읽을 수 있는 공통 포맷. 미디어 타입은 `application/problem+json`. RFC 9457은 2023년 7월에 RFC 7807을 대체했다.

| 멤버 | 의미 | 주의할 점 |
|---|---|---|
| `type` | 문제 '유형'을 식별하는 URI | 없으면 `about:blank` |
| `title` | 유형에 대한 짧은 요약 | 발생마다 바뀌지 않음 (번역 제외) |
| `status` | HTTP 상태 코드 | 참고용 — 실제 응답 코드와 같아야 함 |
| `detail` | 이번 발생에 대한 설명 | 고치는 데 도움 · 디버깅 정보 X · 클라이언트가 파싱 X |
| `instance` | 이번 발생을 식별하는 URI | 보통 요청 경로나 추적 ID |
| 확장 멤버 | `code`, `errors` 등 자유 추가 | 모르는 확장은 클라이언트가 무시 |

이 표준은 **에러 응답만** 다룬다. 성공 응답 래퍼와는 별개다.

출처: RFC 9457 — §3.1 Members, §3.2 Extension Members, §5 Security

### Spring ProblemDetail로 구현하고, 커스텀 DTO와 비교 (슬라이드 18, 데모 C)

```java
private ProblemDetail toProblem(ErrorCode code, String detail, String path) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(code.status(), detail);
    problem.setType(code.type());       // 유형 URI
    problem.setTitle(code.title());
    problem.setInstance(URI.create(path));
    problem.setProperty("code", code.code()); // 확장
    return problem;
}
```

- `setProperty`가 확장 멤버를 추가하는 방법이다. Jackson을 쓰면 Spring이 properties 맵을 펼쳐 최상위 JSON 필드로 쓴다.
- 더 간단히: `spring.mvc.problemdetails.enabled=true`. **Spring 내장 예외만** `ProblemDetail`로 응답한다(직접 만든 예외는 별도 처리 필요). 이미 `ResponseEntityExceptionHandler`를 상속한 Advice를 직접 등록했다면 그쪽이 사용된다.

| 비교 | ProblemDetail | 커스텀 DTO |
|---|---|---|
| 표준 | RFC 9457 | 팀 규칙 |
| Content-Type | `problem+json` | `application/json` |
| Spring 내장 예외 | 기본 지원 | 직접 매핑 |
| 필드 자유도 | 확장 멤버로 | 완전 자유 |
| 기존 프론트 호환 | 전환 비용 있음 | 유지 쉬움 |
| 타임스탬프 등 | 확장으로 추가 | 자유롭게 포함 |

**성공 응답 래퍼(`ApiResponse`)는 그대로 둬도 된다. 표준이 다루는 것은 '에러 응답'뿐이다.**

출처: Spring Framework Reference — Error Responses / 검증: `DemoC_ProblemDetailVsLegacyTest`

### HTTP 상태 코드는 '범주', 에러 코드는 '정확한 원인' (슬라이드 19)

```
404 Not Found                      ← HTTP 클라이언트·프록시·모니터링이 이해
 ├─ MEMBER_NOT_FOUND               ← 앱 로직이 분기하는 기준
 └─ POST_NOT_FOUND
```

**에러 코드 네이밍 규칙 (제안)**
- `{도메인}_{원인}`, 대문자 스네이크 — `MEMBER_DUPLICATE_EMAIL`
- 한 번 공개한 코드는 바꾸지 않는다 (API 계약)
- 메시지와 분리 — 문구가 바뀌어도 코드는 그대로
- 숫자 코드(`E1001`)보다 읽히는 이름이 리뷰·로그에 유리

프론트엔드 사용 예시(개념 예시, TypeScript):

```ts
const res = await fetch("/api/members", { method: "POST", body, headers });

if (!res.ok) {                      // 4xx·5xx만
    const problem = await res.json();
    switch (problem.code) {
        case "MEMBER_DUPLICATE_EMAIL":
            showFieldError("email", problem.title);
            break;
        case "COMMON_INVALID_INPUT":
            problem.errors.forEach(markField);
            break;
        default:
            toast(problem.title);   // 공통 처리
    }
}
```

데모 코드: `common/error/ErrorCode.java`

### 응답에 노출하면 안 되는 예외 정보 (슬라이드 20)

| ✕ 응답에 넣지 않는다 | ✓ 보여줘도 된다 |
|---|---|
| 스택트레이스, 예외 클래스 이름 (`org.hibernate…`) | 불변 에러 코드 (`MEMBER_NOT_FOUND`) |
| SQL 문, 테이블·컬럼·제약조건 이름 | 사용자가 고칠 수 있는 설명 (`detail`) |
| 서버 경로·내부 IP·라이브러리 버전 | 필드별 검증 결과 (`errors[]`) |
| 토큰·비밀번호 등 비밀값 (예외 메시지에 섞여 들어옴) | 추적 ID (`traceId`) — 서버 로그와 연결하는 열쇠 |
| 계정 존재 여부 — '이메일 없음' vs '비밀번호 틀림' 구분은 계정 열거 공격에 쓰인다 | |

Spring Boot 기본값은 `server.error.include-message` / `include-stacktrace` = `never`다. **직접 만든 핸들러가 `e.getMessage()`를 넣는 순간 이 안전장치가 무력화된다.**

출처: RFC 9457 §5 / OWASP Error Handling Cheat Sheet

## PART 6 · 트레이드오프와 적용 (슬라이드 21–23)

### 정답은 없다: 네 가지 반론에 대한 기준 (슬라이드 21)

| 반론 | 기준 |
|---|---|
| 커스텀 예외가 항상 좋은가? | 아니다. 클래스가 폭발한다. 기준은 "클라이언트 분기나 처리가 달라지는가". `BusinessException` 하나 + `ErrorCode` enum으로 시작해도 충분하다. |
| 체크 예외를 써야 하는 경우는? | 호출자가 실제 복구 전략(재시도·대체 경로)을 가질 때 — 외부 연동·파일 I/O 경계. 쓴다면 `rollbackFor`를 함께 점검한다. |
| ProblemDetail vs 공통 응답 DTO? | 새 API·외부 공개 API면 ProblemDetail. 프론트가 이미 DTO에 맞춰져 있으면 무리한 전환보다 계약을 유지하고 버전 단위로 전환한다. |
| 구조가 너무 복잡해지면? | 신호: Advice 순서 의존, 3단 이상 예외 계층, 핸들러 안 `instanceof` 분기. 처방: Advice 하나 + 에러 코드 표 하나. |

출처: RFC 9457 §4 (이미 적합한 도메인 포맷이 있으면 그것을 써도 된다) / dev.java — Unchecked Exceptions

### 우리 프로젝트에 적용한다면 (슬라이드 22)

> 실제 프로젝트 코드는 제공되지 않았으므로, 일반적인 Spring Boot REST API 기준의 **예시**다. 이름은 팀 합의로 확정한다.

**예시 · 에러 계약 표**

| code | status | 프론트 동작 |
|---|---|---|
| COMMON_INVALID_INPUT | 400 | 필드 하이라이트 |
| AUTH_UNAUTHORIZED | 401 | 로그인 화면 이동 |
| AUTH_FORBIDDEN | 403 | 권한 안내 |
| MEMBER_NOT_FOUND | 404 | 빈 상태 화면 |
| MEMBER_DUPLICATE_EMAIL | 409 | 이메일 필드 에러 |
| COMMON_INTERNAL_ERROR | 500 | 재시도 토스트 |

**적용 순서**
1. `ErrorCode` enum + `BusinessException` 도입
2. `GlobalExceptionHandler` 1개 (`ResponseEntityExceptionHandler` 상속)
3. 컨트롤러의 try-catch 제거
4. 에러 코드 표를 문서로 공개하고 프론트와 합의
5. MockMvc로 에러 응답까지 테스트
6. 401/403은 Security의 `AuthenticationEntryPoint`·`AccessDeniedHandler`에서 같은 포맷으로

### 핵심 요약 — 오늘 가져갈 다섯 문장 (슬라이드 23)

1. 복구할 수 없는 비즈니스 오류는 **언체크 + 전역 처리** — 체크 예외는 롤백 규칙을 확인
2. 예상 가능한 결과는 **분기**로, 예외는 예외 상황에만 — 비용의 핵심은 스택트레이스 생성
3. 하위 계층 예외는 경계에서 **의미 있는 예외로 번역하고 `cause`를 보존**
4. 우선순위: **로컬 > Advice(`@Order`) · 가까운 타입 · root > cause**
5. **올바른 HTTP 상태 + 불변 에러 코드 + RFC 9457**, 내부 정보는 로그로만
