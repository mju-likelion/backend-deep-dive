### 멋사 백엔드 스터디 · DB 백업 자동화 편

> 지금까지 우리 앱은 자동 배포되고, 죽으면 알림이 오고, 로그도 관리됩니다. 꽤 그럴듯한 서비스가 됐죠.
> 그런데 정작 제일 중요한 게 아직 무방비입니다. 바로 데이터베이스예요.
> "볼륨에 저장되니까 재배포해도 데이터 안 날아가요"라고 배웠죠. 맞아요. 하지만 그건 재배포에 한해서예요. 서버를 실수로 삭제하거나, 디스크가 고장 나거나, 누가 `DROP TABLE`을 잘못 치면 그동안 쌓인 데이터가 통째로 사라집니다. 그리고 그건 되돌릴 수 없어요.
>
> 오늘은 DB를 자동으로 백업하고, 진짜로 되살릴 수 있는지까지 확인합니다. 목표: 매일 새벽 알아서 백업되고, 사고가 나도 어제 상태로 복구하기.

---

## Part 0. 오늘 할 일 지도

```
[매일 새벽]  cron  ->  mysqldump로 DB 통째로 파일화  ->  오래된 백업 자동 삭제
                                    │
                              (사고 발생 시)
                                    │
                          백업 파일로 복원 -> 어제 상태로 되살아남
```

오늘의 흐름:

1. 볼륨이 있는데 왜 백업이 또 필요한지 이해하기
2. 손으로 백업 한 번 떠보기 (mysqldump)
3. 복원 해보기 (백업은 복원까지 성공해야 진짜 백업이다)
4. 자동화하기 (cron + 스크립트, 오래된 백업 정리)
5. 서버 밖으로 내보내기 (같은 서버에만 두면 서버가 죽을 때 백업도 같이 죽음)

---

## Part 1. 볼륨이 있는데 왜 백업이 또 필요한가

지난 Docker 편에서 배웠죠. DB 데이터는 볼륨에 저장되니 재배포해도 안 날아간다고. 이건 사실이에요. 하지만 볼륨이 지켜주는 건 딱 하나, "컨테이너를 새로 만드는 상황"뿐입니다.

볼륨이 못 지켜주는 상황들:

- 서버(인스턴스)를 실수로 삭제함 -> 볼륨도 같이 사라짐
- 디스크(스토리지)가 물리적으로 고장 남 -> 볼륨째 손상
- 사람 실수 -> `DROP TABLE`, 잘못된 `DELETE`, 마이그레이션 사고
- 침해 사고 -> 데이터가 삭제되거나 암호화됨

정리하면 이렇습니다.

- 볼륨: "컨테이너가 죽어도 데이터를 유지"하는 장치 (재배포 대비)
- 백업: "데이터 자체가 사라지는 사고"에 대비하는 별도 사본 (재난 대비)

둘은 목적이 완전히 달라요. 볼륨이 있다고 백업이 필요 없는 게 아니라, 볼륨과 백업은 서로 다른 사고를 막는 겁니다.

---

## Part 2. 손으로 백업 한 번 떠보기 (mysqldump)

자동화부터 하지 않고, 먼저 손으로 해봅니다. 원리를 알아야 자동화한 게 뭘 하는지 이해되니까요.

MySQL에는 `mysqldump`라는 도구가 있어요. DB 전체를 하나의 SQL 파일로 뽑아내는 명령입니다. 이 파일 하나만 있으면 나중에 그대로 되살릴 수 있어요.

우리 DB는 도커 컨테이너 안에 있으니, 컨테이너 안에서 이 명령을 실행하게 합니다.

### 백업 폴더 만들기

```bash
# 서버에서, 백업 파일을 모아둘 폴더 생성
mkdir -p ~/backups
```

### 백업 한 번 실행

지난 편들에서 DB 비밀번호와 이름은 `.env`에 넣어뒀죠. 그 값을 사용합니다. 프로젝트 폴더에서 실행하세요.

```bash
# 프로젝트 폴더로 이동 (.env가 있는 곳)
cd ~/내프로젝트

# .env의 값들을 현재 셸로 불러오기
set -a; source .env; set +a

# db 컨테이너 안에서 mysqldump 실행 -> 결과를 파일로 저장
docker compose exec -T db \
  mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE" \
  > ~/backups/backup_test.sql
```

> `-T` 옵션은 "터미널을 붙이지 말고 그냥 실행"이라는 뜻이에요. 이걸 안 붙이면 자동화(cron)에서 오류가 납니다. 지금 손으로 할 때부터 붙이는 습관을 들이세요.

### 백업 파일 확인

```bash
# 파일이 생겼고 크기가 0이 아니면 성공
ls -lh ~/backups/

# 내용 앞부분 살짝 보기 (SQL 구문이 보이면 정상)
head ~/backups/backup_test.sql
```

파일 크기가 0바이트면 뭔가 잘못된 거예요 (비밀번호, DB 이름 확인). SQL 구문이 보이면 성공입니다.

## Part 3. 복원 해보기 (제일 중요한 단계)

여기서 스터디원들에게 꼭 강조하세요. 한 번도 복원해본 적 없는 백업은 백업이 아닙니다. 파일이 손상됐거나, 명령이 틀렸거나, 권한이 없어서 정작 사고 났을 때 복원이 안 되는 경우가 실무에서 정말 많아요. 그러니 지금 복원까지 직접 해봅니다.

### 안전하게 연습하는 법

진짜 운영 DB에 바로 복원 연습을 하면 위험하니, 연습용 DB를 하나 만들어서 거기에 복원해봅니다.

```bash
cd ~/내프로젝트
set -a; source .env; set +a

# 연습용 빈 DB 생성
docker compose exec -T db \
  mysql -u root -p"$MYSQL_ROOT_PASSWORD" \
  -e "CREATE DATABASE restore_test;"

# 아까 뜬 백업 파일을 연습용 DB에 복원
docker compose exec -T db \
  mysql -u root -p"$MYSQL_ROOT_PASSWORD" restore_test \
  < ~/backups/backup_test.sql
```

### 복원이 됐는지 확인

```bash
# 연습용 DB의 테이블 목록 보기 (원본과 같은 테이블들이 보이면 성공)
docker compose exec -T db \
  mysql -u root -p"$MYSQL_ROOT_PASSWORD" restore_test \
  -e "SHOW TABLES;"
```

원본 DB에 있던 테이블들이 그대로 보이면 복원 성공입니다. 백업 파일이 진짜로 살아있는 데이터를 담고 있다는 걸 확인한 거예요.

### 연습용 DB 정리

```bash
# 확인 끝났으면 연습용 DB 삭제
docker compose exec -T db \
  mysql -u root -p"$MYSQL_ROOT_PASSWORD" \
  -e "DROP DATABASE restore_test;"
```

> 실제 사고 상황에서는 이 복원을 운영 DB(`$MYSQL_DATABASE`)에 하게 됩니다. 하지만 그건 진짜 급할 때고, 연습은 반드시 별도 DB에서. 운영 DB에 복원하면 현재 데이터를 백업 시점으로 덮어쓴다는 걸 기억하세요.

## Part 4. 자동화하기 (cron + 스크립트)

원리를 이해했으니 이제 매일 자동으로 백업되게 만듭니다. 지난 모니터링 편에서 쓴 cron을 다시 활용해요.

### 백업 스크립트 작성

```bash
nano ~/backup.sh
```

내용:

```bash
#!/bin/bash

# 프로젝트 폴더로 이동해서 .env 불러오기
cd ~/내프로젝트
set -a; source .env; set +a

# 백업 폴더와 날짜별 파일명 준비
BACKUP_DIR=~/backups
DATE=$(date +%Y%m%d_%H%M%S)
FILE="$BACKUP_DIR/backup_$DATE.sql"

# 백업 실행
docker compose exec -T db \
  mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE" > "$FILE"

# 백업 파일 압축 (용량 절약)
gzip "$FILE"

# 7일보다 오래된 백업은 자동 삭제 (디스크 관리)
find "$BACKUP_DIR" -name "backup_*.sql.gz" -mtime +7 -delete

echo "백업 완료: $FILE.gz"
```

저장 후 실행 권한 부여:

```bash
chmod +x ~/backup.sh
```

> 이 스크립트가 하는 일: 날짜가 붙은 이름으로 백업 -> 압축 -> 7일 지난 백업 삭제. `find ... -mtime +7 -delete`가 오래된 걸 자동 정리해줘서, 백업 파일이 무한정 쌓여 디스크를 채우는 걸 막아요. 지난 로그 편에서 배운 "디스크 꽉 참 방지"와 같은 맥락입니다.

### 먼저 손으로 한 번 돌려보기

```bash
# cron에 걸기 전에 스크립트가 잘 도는지 직접 실행
~/backup.sh

# 압축된 백업 파일이 생겼는지 확인
ls -lh ~/backups/
```

### cron에 등록 (매일 새벽 4시)

```bash
crontab -e
```

맨 아래에 추가:

```
0 4 * * * ~/backup.sh
```

> `0 4 * * *`는 "매일 새벽 4시 정각"이라는 뜻이에요. 사용자가 적은 시간대에 백업을 돌리는 게 좋습니다. 이제 매일 새벽 알아서 백업이 뜨고, 일주일 지난 건 알아서 지워집니다.

## Part 5. 서버 밖으로 내보내기 (오프사이트 백업)

여기 중요한 맹점이 하나 있어요. 지금 백업 파일은 전부 같은 서버 안(`~/backups`)에 있습니다. 그런데 우리가 백업으로 대비하려던 사고가 뭐였죠? "서버나 디스크가 통째로 날아가는 것"이었어요.

서버가 죽으면 그 안의 백업도 같이 죽습니다. 같은 배에 구명보트를 실어둔 셈이에요.

그래서 실무에서는 백업을 서버 밖 다른 곳에 한 벌 더 보관합니다. 이걸 오프사이트(off-site) 백업이라고 해요.

방법은 여러 가지가 있고, 오늘은 개념만 잡습니다.

- 클라우드 저장소로 업로드: AWS S3 같은 곳에 백업 파일을 올림. 서버가 죽어도 S3의 사본은 살아있음. 스크립트 마지막에 업로드 명령 한 줄을 추가하는 식으로 확장 가능.
- 다른 서버/내 컴퓨터로 전송: `scp`나 `rsync`로 주기적으로 복사.

> 스터디에서는 우선 "같은 서버 안 백업(Part 4)"까지 확실히 손에 익히고, 오프사이트는 "이게 없으면 진짜 재난 때 백업이 무의미해진다"는 개념만 확실히 이해시키는 걸로 충분합니다. S3 연동은 AWS 자격증명 설정이 필요해서, 3막 인프라 편에서 다루는 게 흐름상 자연스러워요.

백업의 원칙 하나만 기억하면 됩니다. 흔히 3-2-1 규칙이라고 불러요. 사본을 최소 3개, 서로 다른 저장 매체 2곳에, 그중 1개는 물리적으로 떨어진 곳에 둔다. 지금 우리는 서버 안 백업까지 왔고, 오프사이트를 더하면 이 원칙에 가까워집니다.

## Part 6. 자주 나는 에러 & 해결법

**증상: 백업 파일이 0바이트로 생김**
원인: 비밀번호나 DB 이름이 틀림, 또는 `.env`를 안 불러옴.
해결: `set -a; source .env; set +a`를 실행했는지 확인. `echo $MYSQL_DATABASE`로 값이 제대로 들어왔는지 확인. 비밀번호에 특수문자가 있으면 따옴표 처리를 확인.

**증상: `the input device is not a TTY` 오류**
원인: `docker compose exec`에 `-T` 옵션을 안 붙임. 특히 cron에서 발생.
해결: 명령에 `-T`를 추가. 자동화에서는 필수.

**증상: cron으로는 백업이 안 되는데 손으로는 됨**
원인: cron은 실행 환경이 달라서 `~`나 상대경로, 환경변수를 못 찾는 경우가 많음.
해결: 스크립트 안에서 `cd ~/내프로젝트`처럼 경로를 명시하고, crontab 경로도 절대경로(`/home/ubuntu/backup.sh`)로 쓰는 게 안전. `grep CRON /var/log/syslog`로 실행 여부 확인.

**증상: 복원했는데 데이터가 이상하거나 깨짐 (한글 등)**
원인: 문자셋(character set) 불일치.
해결: 백업/복원 시 DB의 문자셋(보통 utf8mb4)이 일치하는지 확인. mysqldump는 기본적으로 문자셋 정보를 포함하지만, 컨테이너 설정이 다르면 문제가 생길 수 있음.

**증상: 백업 파일이 계속 쌓여 디스크를 먹음**
원인: 오래된 백업 삭제 로직이 없거나 동작 안 함.
해결: 스크립트의 `find ... -mtime +7 -delete`가 들어있는지 확인. 보관 기간(7일)은 상황에 맞게 조정.

## 오늘의 3줄 요약

1. 볼륨과 백업은 다른 사고를 막는다. 볼륨은 재배포 대비, 백업은 서버 삭제·디스크 고장·사람 실수 같은 재난 대비. 볼륨이 있어도 백업은 반드시 필요하다.
2. 백업은 복원까지 성공해야 진짜 백업이다. mysqldump로 뜨고, 연습용 DB에 복원해서 데이터가 살아있는지 반드시 확인한다. 한 번도 복원 안 해본 백업은 백업이 아니다.
3. cron으로 매일 자동 백업하고 오래된 건 자동 삭제한다. 그리고 백업을 같은 서버에만 두면 서버가 죽을 때 같이 죽으니, 서버 밖(오프사이트) 사본이 진짜 안전장치다.

이제 여러분 서비스는 사고가 나도 되돌아갈 수 있는 안전장치를 갖췄습니다. 1막에서 배운 배포와 운영의 기본기가 여기서 완성됐어요.
